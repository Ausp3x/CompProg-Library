# 02-search_algorithms.hpp — evidence

`02-search_algorithms.hpp` covers the Basic search row. The legacy names `binSearch` and `ternSearch` remain; the legacy real point searches map to the bracket forms (Legacy mapping). The header adds endpoint-independent first/last-true searches, Fibonacci and exponential integer searches, golden-section minimization, and real bracket/result interfaces. Every function is stateless, and every caller predicate or objective must be deterministic.

## Contracts

### binSearch

`binSearch(ok, ng, f)` accepts any two `lng` endpoints, in either order. The caller knows `ok` is feasible and `ng` infeasible, with one monotone transition between them. Neither endpoint is evaluated, so they may stand for hypothetical boundary states. Equal endpoints mean the answer has already converged. The function returns the last feasible value next to the transition and makes at most 64 predicate calls. It equals `lastTrue(ok + 1, ng, f)` when `ok < ng` and `firstTrue(ng + 1, ok, f)` when `ok > ng`, mapped to `ok` when nothing qualifies; it stays as the one orientation-free call for the ok/ng idiom (`00-Guidelines/23-Sweep Ledgers/duplicates.md`, Keeps).

Correctness: `std::midpoint` rounds toward `ok`; when the midpoint equals `ok`, the endpoints are adjacent or equal. Every queried midpoint is strictly interior, and updating one endpoint keeps the transition bracketed. This avoids the archived `abs(ok - ng)` overflow even for `INT64_MIN` and `INT64_MAX`.

### firstTrue, lastTrue

Both search half-open `[l, r)` with `l <= r` (asserted). `firstTrue` needs a false-then-true predicate and `lastTrue` a true-then-false one. Both return `{found, position}`, with `{false, r}` for absence, including empty ranges. Neither endpoint is a sentinel. `r = INT64_MAX` stays a valid excluded endpoint. No search here tests `INT64_MAX` itself as a candidate, since an excluded bound cannot pass it; `binSearch` excludes `ng` the same way.

Correctness: each midpoint satisfies `l <= md < r`, so `md + 1` cannot overflow. `lastTrue` finds the first false position and decrements it only when it exceeds `l`.

### ternSearch, fibSearch

Both take the legacy **closed** interval `[l, r]` with `l <= r` (asserted), including either signed extreme and singletons. The function must strictly decrease, then may stay flat at its minimum, then strictly increase; either strict side may be empty. Flat stretches away from the minimum break this contract. Both return the **leftmost** minimum and need values only to support `<`.

- `ternSearch` makes at most `2 * ceil(log2(n))` evaluations, 128 over the full domain.
- `fibSearch` makes at most `log_phi(n + 1) + 1` evaluations, 92 over the full `lng` domain. That is about 1.44 log2 n against 2 log2 n, which matters when the objective is expensive. A singleton returns without evaluating.

Correctness of `ternSearch`: it compares neighbours at `md` and `md + 1` (safe since `md < r`). A decrease puts the first minimum to the right; otherwise it is at or left of `md`. This halves the interval each step, where the archived ternary reduction kept two thirds.

Correctness of `fibSearch`: it keeps an open window `(a, b)` with `b - a = y`, where `x < y` are consecutive terms of 2, 3, 5, 8, … and the leftmost minimum lies inside. It starts at `a = l - 1` with the least `y >= n + 1` (at least 3) and probes `c = a + y - x < d = a + x`. If `f(c) <= f(d)`, the leftmost minimum is in `(a, d)` (strict: `d` is on the increasing side; equal: both probes are on the flat minimum or on opposite sides of it). Otherwise `c` precedes the leftmost minimum, which is in `(c, b)`. The window shrinks to length `x` and the surviving probe is one of the two new probes, so each step costs one evaluation. Probes beyond `r` read `f(r)`, extending the function with a flat tail; both cases stay valid because the leftmost minimum is at most `r`, and a probe `c <= r < d` with `f(r) < f(c)` cannot have reached the minimum. At `y = 3` the window holds exactly `c` and `d`. With `F_k` the least term of 3, 5, 8, … with `F_k >= n + 1`, the search makes `k - 1` evaluations; minimality and Binet's formula give at most `log_phi(n + 1) + 1`, also checked numerically through `n = 2000` and at `2^64`. Positions are `lll`, so `n = 2^64` is representable.

### expSearch

`expSearch(ok, f)` gallops upward from a known-true `ok`, which is never evaluated. `f` must be true then false on `[ok, INT64_MAX]`. The function returns the last true value, or `INT64_MAX` when `f` never becomes false. It makes at most about `2 * log2(answer - ok + 2) + 2` evaluations and needs no upper bound in advance. For a downward search, negate the argument inside `f`.

Correctness: each round tests `ok + d` with `d = 1, 2, 4, …` and moves `ok` there while true. The step is clamped to `INT64_MAX` once the gap `INT64_MAX - ok`, computed in `ulng`, is at most `d`. The first false probe brackets the transition for `binSearch`. Because the gaps 1, 2, …, 2^63 sum past every distance, `ok` reaches `INT64_MAX` before `d` can wrap.

### RealSearchResult

The result holds the sorted closed bracket `[l, r]`, the recommended point `x`, the number of completed reductions in `iterations`, and `converged`. `converged` is true exactly when

```
r - l <= abs_tol + rel_tol * max(abs(l), abs(r))
```

or no binary64 value lies strictly inside `[l, r]`. `l` and `r` are endpoints or probe points as computed, zero signs included; bisection returns `min(ok, ng)` and `max(ok, ng)` of its last pair, so a bracket of two zeros returns `ok`'s zero as `l`, `r` and `x`. False means the iteration cap was reached or the interpolation stagnated. The width and point guarantees assume reliable comparisons of `f`; this is not interval arithmetic.

### search_detail::validate, search_detail::done

`validate` asserts finite endpoints, `itr >= 0`, and finite nonnegative tolerances. `done` is the `converged` predicate above, evaluated in `long double` so that opposite-sign endpoints and tolerance products cannot overflow. `bisect(ok, ng, f, mid, ...)` is the shared real bisection loop of `binSearchRealBracket`, `binSearchRealGeometric` and `binSearchRealBits`: it validates, splits at `mid(ok, ng)`, and stops at the cap or at `done`. `mid` must return a point strictly inside a bracket that is not done: `std::midpoint` of two doubles with one strictly between them is correctly rounded and so strictly inside, and the geometric split falls back to it.

### binSearchRealBracket

Finite true and false endpoints come in either order and are never evaluated; equal endpoints are already converged. `x` is the true endpoint. In exact arithmetic the width after `k` reductions is `initial_width / 2^k`. Each reduction makes one predicate evaluation, at most `itr` in total. `itr` defaults to 100.

### binSearchRealGeometric

The same contract as `binSearchRealBracket` for endpoints that are finite, nonzero and of one sign (asserted), splitting at the signed geometric mean `copysign(sqrt(|ok|) * sqrt(|ng|), ok)` instead of the midpoint. In exact arithmetic `log(r / l)` halves per reduction, so relative precision `epsilon` over a ratio `R` takes about `log2(ln(R) / epsilon)` reductions: the whole positive range `[denorm_min, DBL_MAX]` reaches adjacent doubles in at most 65 reductions, where midpoint bisection needs up to about 2,100. When rounding puts the geometric mean on or outside an endpoint (brackets a few ulps wide) the step falls back to `std::midpoint`, so the search ends only at adjacent doubles, the tolerance or the cap. The product of square roots cannot overflow or underflow to zero. A threshold at or near zero takes `denorm_min` as its false endpoint (with `abs_tol` for an absolute stop): maspypy's mixed absolute/relative search (`binary_search_real_abs_rel`, arithmetic below 1, geometric above) is covered that way.

### binSearchRealBits

The same contract as `binSearchRealBracket` for any finite endpoints, zero and mixed signs included, splitting at the median double of the bracket: the doubles map to `lng` by their bit patterns, negative patterns reflected below zero (`INT64_MIN - i`; both zeros go to 0, and the same map takes every other key back to its double and 0 to `+0`), and the split is `std::midpoint` of the two keys, rounded toward `ok`, mapped back. The map preserves order, so each reduction halves the number of doubles in the bracket: adjacent doubles within 64 reductions on any finite bracket, `[-DBL_MAX, DBL_MAX]` included; `itr` defaults to 100. A bracket with a double strictly inside has keys at least 2 apart, so the split is strictly inside. Relative to `binSearchRealGeometric` it needs no sign restriction, and it takes up to 51 more reductions on ranges reaching into the subnormals, where the keys are linear, and at most 2 fewer elsewhere ([00-notes.md](00-notes.md), P012 MA01).

### ternSearchRealBracket, goldenSearchRealBracket

Both take finite `l <= r` and the same strict-side, optional-flat-minimum shape as `ternSearch`. Comparisons must preserve that shape, so NaN values are not allowed. The returned bracket intersects the set of minimizers, and `x` is its rounded midpoint. It is not promised to be the leftmost point of a continuous plateau. Ties keep the left part: when the two probe values are equal, the part right of the right probe is dropped, so a constant objective keeps `l`.

- Ternary search shrinks the width by `2/3` per reduction at two evaluations each, at most `2 * itr`.
- Golden search shrinks it by `(sqrt(5) - 1) / 2` per reduction and caches one value. It makes zero evaluations when the bracket is already done or `itr = 0`, and at most `itr + 1` otherwise. The new probe is placed as in Numerical Recipes 10.2, `lerp(kept, far end, 0.381966...)` from the kept probe, never from the far end alone: recomputing both from `l` and `r` lets the cached probe drift from the golden proportion by a factor phi per reduction, and on `[-DBL_MAX, DBL_MAX]` the probe order broke after 111 reductions with the bracket still about `1.5e285` wide. With the stable placement the probes stay in order until the bracket is a few ulps wide. The tester replays the probe sequence against an independent reference.

Correctness of the real searches: `std::midpoint` and `std::lerp` avoid overflowing `r - l` in binary64. Every successful reduction keeps ordered interior probes, and golden search checks that order before reusing cached values. Ternary and golden interpolation may stall before the endpoints become adjacent; the result is then the remaining bracket with `converged == false`, unless the tolerance was met anyway. Reaching a positive absolute width `epsilon < W` in exact arithmetic takes `ceil(log(W / epsilon) / log(1 / q))` reductions, `q` being 1/2, 2/3 or `(sqrt(5) - 1) / 2`. Rounding limits the useful precision, so the actual bracket and status are reported rather than a fixed iteration count. A purely relative tolerance near zero may be unattainable within the cap.

`itr` defaults to 200 for ternary (legacy) and 100 for golden. To maximize, minimize a reversed objective whose evaluation stays valid, such as a negated real objective. Negating `INT64_MIN` is not valid.

### brentSearchRealBracket

Brent's minimization (Numerical Recipes 10.2 `brent`): golden-section steps, replaced by the vertex of the parabola through the three best points when that step lands inside the bracket and is shorter than half the step before last. Domain: finite `l <= r`, the `ternSearch` shape, and an objective returning a real number (`double` or `long double`), since the parabola subtracts values. The returned bracket intersects the minimizer set, as for golden search; `x` is the evaluated point with the least value (the first evaluation is at the golden point `lerp(l, r, 0.381966...)`), or the bracket midpoint when it made no evaluation (`itr = 0`, an already converged bracket, or no interior golden point). It makes at most `itr + 1` evaluations; `iterations` counts those after the first. `itr` defaults to 100. The probe sequence is NR's, with its tie rules: `f(u) <= f(x)` makes `u` the new best point; otherwise `u` replaces `w` when `f(u) <= f(w)` or `w == x`, else `v` when `f(u) <= f(v)`, `v == x` or `v == w`. The tester replays it against an independent reference.

Steps are at least `tol1 = max((abs_tol + rel_tol * |x|) / 4, 2 * DBL_EPSILON * |x| + denorm_min)` from `x`, and parabolic steps closer than `2 * tol1` to an end move `tol1` toward the midpoint, as in NR: the floor keeps every probe a distinct double. The bracket meets the tolerance when its two sides are within about `2 * tol1`. With zero tolerances the search stops when the next probe is not strictly inside the bracket or equals `x`, usually a few ulps from `x` with `converged == false`; NR's default `tol = 3e-8` (about `sqrt(DBL_EPSILON)`) is the useful precision for a smooth minimum, where `f` is flat to rounding over that width. The parabola and step lengths are computed in `long double`, so `[-DBL_MAX, DBL_MAX]` brackets and large objective values do not overflow.

Correctness: every probe `u` lies strictly inside `(l, r)` and differs from `x`, which stays strictly inside. If `f(u) <= f(x)` the side beyond `x` away from `u` is dropped, otherwise the side beyond `u`; under the shape contract the dropped part holds a minimizer only when the kept part does too (a weak inequality between two points on one side of a minimizer forces both onto the flat minimum), so the bracket keeps meeting the minimizer set, exactly as in golden search. The interpolation only chooses `u`, so it affects speed, never this invariant. The bracket strictly shrinks at each evaluation, so the loop ends within `itr` steps. On a smooth objective the parabolic steps converge superlinearly (order about 1.32); on a quadratic the tester sees 6 evaluations where golden search needs 63 to the same tolerance.

### brentSearchRealBracketDerivative

Brent's minimization with derivatives (Numerical Recipes in C 2nd ed. 10.3 `dbrent`, NR3 `Dbrent`): the domain, result fields, start point, `tol1`, tolerances, stopping rule and evaluation bound of `brentSearchRealBracket`, with `df` the derivative of `f` (a subgradient at a kink serves). Each step takes a secant step toward `df = 0` through `x` and `w`, or through `x` and `v`, the shorter of those strictly inside the bracket and downhill (`df(x) * d <= 0`), when it is at most half the step before last; otherwise it halves the side the derivative points downhill to. Every iteration calls `f` and `df` once each at the same point, so both make at most `itr + 1` calls. When the probe would leave the bracket because the downhill side is narrower than `tol1`, the probe moves `tol1` to the other side of `x`, and only a strictly lower value there replaces `x`: a tie or a higher value closes the bracket to about `2 * tol1`, which is NR's stop after an uphill minimal step, expressed through the bracket. Without the tie rule, an objective flat to rounding near its minimum (`exp(-2x) + x`, `-sin`) walked across the flat part in steps of `tol1`. A tie keeps the bracket valid: under the shape contract `f(u) == f(x)` puts a minimizer between them. The `v` update uses NR's strict `f(u) < f(v)`. The tester replays the probe sequence against an independent reference.

Correctness: the bracket is updated from function values only, exactly as in `brentSearchRealBracket`, so it keeps meeting the minimizer set whatever `df` returns; a wrong derivative only slows the search (with `df = 0` it halves toward `l` forever and can leave `x` far from the minimizer within `itr`). With a correct derivative on a simple smooth minimum the secant steps converge superlinearly. On a degenerate minimum, where `f'` has a multiple root (`(x + 0.7)^4`), they converge only linearly and take more calls than Brent's parabolas. Calls of `f` to `abs_tol = 1e-12` (itr 200), against Brent's: 5 against 6 on three quadratics, 8 against 20 on `cos(x) + 0.1 x`, 14 against 23 on `exp(-2x) + x`, 9 against 41 on `-sin` over `[0, pi]`, 13 against 12 on `y^4 + y^2`, 117 against 24 on `(x + 0.7)^4`. Slower alternative: cubic interpolation of values and derivatives (Davidon), which NR discusses and rejects without a routine, is not kept (`Docs/00-notes.md`, P012 MA01).

## Benchmarks

No timing benchmark. `fibSearch` makes at most `log_phi(n + 1) + 1` evaluations, against `2 * ceil(log2(n))` for `ternSearch`; `brentSearchRealBracket` converges superlinearly on smooth objectives (6 evaluations against golden search's 63 on the tester's quadratic), and `binSearchRealGeometric` needs at most 65 reductions over the whole positive range against about 2,100 for midpoint bisection; the evaluation counts are the cost evidence. No Barrett/Montgomery or ISA-specific code is used.

## Limits and handoffs

- `OLD/5-Mathematics/02-search.hpp` and `OLD/Team Notebook/src/math/search.hpp` are unchanged. Their known-true endpoint result, closed integer minimization and iteration arguments remain available; real point interfaces are `.x` of the bracket forms.
- Root finding beyond predicate bisection belongs to `17-numerical_methods.hpp`, and batched parallel binary search to Miscellaneous `20-parallelbinarysearch.hpp`.
- Unbounded downhill bracketing (NR `mnbrak`) is planned in row 69 as `bracketMinimum` (user decision 2026-11-12).
- One equivalent mutant, `COS 736`, rests on probe evidence with an argument, not a proof: the geometric split never rounds outside its bracket (Mutation testing).
- Mutants `COS 616`, `COS 711`, `COS 756` and `COS 1209` (Mutation testing) are recorded survivors (user decisions 2026-11-12 and 2026-11-13): they leave the operation's bound only under `NDEBUG` past a violated `l <= r` or `itr >= 0`, which no test may exercise.
- Under FMA contraction (`-march=native`) `std::lerp` rounds once, so the golden start of Brent and dbrent can differ from a separately rounded build by a few ulps of `max(abs(l), abs(r))`, and ternary search can stop at once on a three-double bracket across a negative binade edge, as documented for stagnation; the native build covers both (user decision 2026-11-13).
