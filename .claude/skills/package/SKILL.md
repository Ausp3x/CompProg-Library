## Workflow

Work through every step. The brief at the end is the whole scope; do not open other packages, whole inventories or the JSON maps. A verified package with open follow-ups (the brief lists them) has only those as scope: run the steps they need, and in step 11 close each one done with `plan.py follow-up Pxxx --done <n>` instead of `set`.

1. **Model and prerequisites.** First run `python3 .claude/hooks/harness.py --selftest`; if it prints FAIL, stop and show its FAIL lines, since the model guard is inactive. Then act on the brief:
   - its first line reports a MISMATCH, or this session's model differs from the brief's: stop and give the user the brief's launch command (user decision 2026-11-26);
   - it names a batch to run instead: stop and give the user that command;
   - a prerequisite WARNING: stop and report which package must run first; you may still do independent owned work;
   - STOP (claimed by someone else, or maintainer-only): stop and report it;
   - Unclaimed or Claims unknown: give the user its claim commands and continue once they confirm;
   - Claimed by you with a switch: stop, give the user that command and rerun the brief on the claim branch;
   - a commit-hook WARNING at the brief's end does not stop the run: give the user its command.
2. **Context.** Read the target headers that exist, the evidence documents linked in the brief, the folder's `Docs/00-notes.md` if present, and the legacy excerpts the brief names. Rules for the files you touch load automatically when you open them. If `00-Guidelines/23-Sweep Ledgers/duplicates.md` has a section for this package, settle its `ask` rows in step 10's round of questions as `/prune` (Procedure) describes.
3. **Completeness research.** For each target row delegate to `@researcher` with the folder, the header name and the row's operation list. It returns operations present in the reference catalogs but absent from the row, with sources, and for `02`–`07` rows the `slower` alternatives with their reasons (`01-principles.md`, Priority). Operations already in the row stay in scope (the `/omission-sweep` decisions in `00-Guidelines/23-Sweep Ledgers/omissions.md` bind). Add every operation the rules admit to the row before implementing, the weak cases too (`01-principles.md`, Scope Discipline, Conservative default), and cite the sources in `<folder>/Docs/00-sources.md`; one that needs another model, package or source becomes a follow-up on its owner (`plan.py follow-up`), named in the report. List `aliases` in the evidence document only, in a form `grab --find` reads (`96-Local Testing/Docs/00-search.md`, Contracts).
4. **Implement** every operation in each row under the applicable rule (`03-cpp.md` or `04-python.md`) and the profile from `01-principles.md`. Keep legacy originals untouched. Never port or add a same-context form or second implementation (`03-cpp.md`, One API per Operation); a wrapper in another context or a named composition calls what it wraps; map each old name to its replacement in the evidence document. If `00-Guidelines/23-Sweep Ledgers/duplicates.md` has a section or a recorded change for this package, apply it as `/prune` steps 2 to 5 describe and record it there as its step 8 does.
5. **Tests** per `05-testing.md` (one entry per header or module, real quick/full/stress coverage, independent oracles, its case classes and builds, memory caps); a `01-Core` tester joins `QUICK` in `96-Local Testing/01-run.py`. Delegate writing a tester to a general-purpose subagent (header path, row operations, contracts, `05-testing.md`); it returns the tester path, its feature-to-test map and the commands it ran. Check the map against the row, and keep failure analysis and fixes here. While working, run the testers in full mode on the local `g++` (`05-testing.md`, Package Checks).
6. **Benchmarks** when the profile or the Barrett/Montgomery rule requires them; record conditions and medians. Delegate the runs the same way; they return both. A Core full header's package first decides every optimization candidate by the sweep rules of `05-testing.md` (Benchmarks, Schedule), measuring in this session.
7. **Final checks** once the code is finished, each once (`05-testing.md`, Package Checks): full, full with `CXX=g++-14`, one stress round, the extraction checks, the integration build, and the mutation campaign of every header the package adds or changes with `run_in_background`, its survivors classified in this session (`05-testing.md`, Mutation Testing). A SKIP (no mewt) leaves the package `in-progress`. A required run starts without asking.
8. **Evidence document** `<folder>/Docs/<NN-name>.md` for each header, with the content and latest-run form `02-structure.md` (Names) defines, including the exact commands, its Limits and Handoffs, and beside the latest run's date the session's experiment exactly as `python3 .claude/hooks/harness.py --experiment` prints it.
9. **Bookkeeping**: update the inventory row operations and status with evidence links; update `998-basic.hpp`/`999-all.hpp` or the Python aggregates; once a row is verified, delete its `97-Legacy` excerpt (`02-structure.md`, Archive); if the Core template or debug header changed, run `python3 '97-Online Testing/03-workspace.py'` then `--check`.
10. **Independent review**, the package's one full audit: delegate to `@reviewer` with the brief's id and the model and effort `CLAUDE.md` gives it (its procedure holds the per-operation checklist and the Limits split), naming what to review, never what not to flag. Fix every confirmed finding and rerun the checks its files affect (`05-testing.md`, Package Checks); ask every open decision in one round and carry out the answers; then record the review, its report on standard input: `python3 .claude/skills/finish/gaps.py --reviewed <id>`, adding `--wrong` when it confirmed a wrong answer or undefined behavior. `/finish` reviews only what changed since.
11. **Record and validate.** `python3 '00-Guidelines/13-Plan/plan.py' set Pxxx verified --evidence <paths> --note '<what stays true, or empty>'`, which replaces the progress note and refuses a limit without a user decision; if any operation is missing, use `partial` on the row, `in-progress` on the package, and `--note` with the exact remaining work and the failing reproducer, if any. Then `python3 '96-Local Testing/03-consistency.py'` must print no errors.
12. **Reap**: once nothing of this session should keep running (no subagent or background task), run `python3 .claude/skills/reap/reap.py --own --scratchpads`; it ends what this and ended sessions left running and deletes stale test temporaries and the scratchpads of sessions ended and idle for 24 hours.
13. **Land or hand over.** Run `python3 .claude/skills/finish/gaps.py <id>`. When the package or batch is recorded as step 11 says and the facts show nothing open (the review record covers the current files; Undecided limits, Follow-ups, Sources, Undecided optimization, Mutation records, Agent-made omissions, Open sweep and TODO markers show `(none)`; any Comparison record is current), land it now as `/finish` step 7 does, a contributor on the claim branch, with step 10's review in the finish-log line (user decision 2026-11-26). Otherwise land nothing and tell the user to run `/clear`, then `/finish` with the brief's id. Then report: operations implemented, commands run with pass/fail, benchmark headlines, review findings fixed, remaining gaps, the landing result with the push commands, the reap's ENDED, LEFT and FAIL lines, and last the two lists `01-principles.md` (Scope Discipline) ends every report with. No file dumps.

## Context Discipline

- Never paste a header, a test log or an inventory into a reply; refer to paths and line numbers.
- Run testers with output redirected to a file in the session scratchpad and read only the failing lines. A `FAIL memory cap` means unbounded allocation or an oversized mode: fix the cause.
- State lives in files, so a compaction (`CLAUDE.md`, Compact Instructions) or a fresh session loses nothing: after steps 3, 4, 5, 6, 7 and 10, record the operations done and remaining, open decisions, failing reproducers with seeds and the exact next step with `plan.py set Pxxx in-progress --note "..."` (`verified` in a follow-up run), keeping whatever in the existing note is still open, and keep the evidence document current.

## Batches

A package with several batches runs one batch per session, always under its batch id; a package id's brief only names the next open batch. Complete the batch the same way, then, unless it was the package's last open batch, set the package `in-progress` with a note naming the finished batch and the next one instead of step 11's `verified`.
