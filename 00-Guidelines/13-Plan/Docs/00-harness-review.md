## Contracts

### Settings (`.claude/settings.json`, `.claude/settings.local.json`)

- `worktree.baseRef: "head"`: new worktrees, including `--worktree` sessions and isolated subagents, branch from the local `HEAD` (inside a worktree, that worktree's `HEAD`), so unpushed commits on `master` carry over and nothing needs a push first. `01-prompts.md` (Workflow) and `AGENTS.md`, whose manual recipe now branches from `HEAD`, say so.
- `skillOverrides`: claude-api, dataviz, artifact-design, artifact-diagramming, artifact-capabilities, run, init, schedule, plugin-authoring and security-review are `"user-invocable-only"` (hidden from Claude, `/name` still runs them); workflow-authoring and update-config are `"on"`. Reason (user decision 2026-11-19): the skill listing took about 14,000 characters a session for 27 skills, and claude-api loaded itself 5 times at about 105–114 KB each, while none of these serves library work.
- `enableArtifact: false` turns the Artifact tool off for every session of the project; no file can turn it back on.
- `syncClaudeAiSkills: false` sits in `.claude/settings.local.json` (git-ignored), since the key's scope is user, local or managed and a project value is ignored. It applies to this clone only; another clone sets it in its own local or user settings. In local settings Claude Code stops loading the synced skills but does not move them to `~/.claude/skills/.trash/`.
- `includeGitInstructions` stays on, so sessions keep the git status snapshot.

### Hooks

- **PreCompact** (`resume.py precompact`, no matcher, timeout 60 s): stdout becomes instructions for the compaction summary, which Claude Code caps at 10,000 characters per hook; the script keeps under 9,000. It names the target (the batch or package id of the session's last typed `/package`, `/prune` or `/finish` call, else the branch or worktree name, through `gaps.py`'s `target()`), says which of the two named it (the typed command that gave the argument, cut to 80 characters so the later lines always fit), names the skill to resume and asks for its step number and the exact next step, gives the `/finish` ledger path (existing or not yet written; no line without a target or ledger) and the keep and drop lists of `CLAUDE.md` (Compact Instructions). It always exits 0: exit 2 would block the compaction, and a failure prints nothing. It shares `last_command()` and `ledgers()` with the `compact` SessionStart mode; `/pause` (`pause.py`) uses `last_command()` too.
- **Notification** (`notify.py`, matcher `permission_prompt|idle_prompt`, timeout 10 s): a notification titled `Claude Code · <name>` with the body `<why>[: <message>]`, where the name is the newest `custom-title` record in the transcript, read backwards in 1 MiB chunks (set by `--name` or `/rename`; Notification input carries no title) and otherwise the checkout folder with its branch, and the reason is "waits for your permission", "waits for your input" or "needs attention". The notifier is `notify-send --app-name=Claude Code` on Linux, `terminal-notifier` (else `osascript`'s `display notification`) on macOS, and a toast through `powershell.exe` with the Windows PowerShell app id on Windows and WSL (detected by `WSL_DISTRO_NAME` or a `microsoft` kernel release). It is silent when the notifier is missing, fails or hangs, and on malformed input; its git calls (2 s each) and the notifier (8 s) share a 9 s deadline inside the hook's 10 s; Claude Code ignores this hook's exit code. Claude Code fires these types only when the user seems away: `permission_prompt` after about six seconds without a keystroke, `idle_prompt` once `messageIdleNotifThresholdMs` (user scope in `~/.claude.json`, default 60000; the user set 30000 on this machine, user decision 2026-11-23) passes after a reply with no keypress, click or terminal focus change since it ended and no background agent running (Claude Code 2.1.330's code).
- **Click to focus** (user decision 2026-11-23): in the terminal of VS Code or an editor built from it (`TERM_PROGRAM=vscode`: Insiders, VSCodium, Cursor) a click on the notification brings forward the editor window holding the session's folder. The editor is the one whose `product.json` sits four folders above its git extension's askpass script (`VSCODE_GIT_ASKPASS_MAIN`); its non-empty string keys `nameShort` (settings folder), `nameLong` (window title), `applicationName` (launcher) and `urlProtocol` (toast link) are used, and a key it lacks disables the step that needs it instead of falling back to VS Code's value, so a click never opens another editor. Without a readable `product.json` VS Code's values apply. The folder is the deepest window folder in that editor's `storage.json` (`windowsState`; Linux under `$XDG_CONFIG_HOME` or `~/.config`, macOS under `~/Library/Application Support`, Windows under `%APPDATA%`, WSL in every Windows user's roaming folder, keeping this distribution's `vscode-remote://wsl+<distro>` windows) containing the working directory, else the main checkout (`git rev-parse --git-common-dir`), so a linked worktree's session finds its checkout's window. Opening a folder that a window already holds focuses that window. On Linux, when `notify-send --help` lists `--action` (libnotify 0.7.10), the hook starts a helper in its own session with `CP_REAP_KEEP=1` and returns: the helper shows the notification with a default action (`--action=default=Open`), waits up to 600 s, then sends SIGINT so that notify-send closes it, and on a click runs the launcher (from the editor's own `bin` folder, else `PATH`) on the folder. The launcher gets the hook's environment without the variables of the Claude Code session (`CLAUDE*`, `CP_USER`, `CP_REAP_KEEP`, `AI_AGENT`), inherited activation tokens and `VSCODE_*` other than `VSCODE_IPC_HOOK_CLI`, since a window it opens takes that environment. On KDE (`XDG_CURRENT_DESKTOP` lists `KDE`) the helper first has KWin activate the window: a one-shot KWin script, loaded, run and unloaded over D-Bus (`gdbus`, else `qdbus6` or `qdbus`), unminimizes and activates the first normal window whose title holds ` - <folder name> - ` and ends with the editor's `nameLong`, as VS Code's default `window.title` reads. It runs before the launcher, which took 1.1 s against 13 ms for the script. Reason: a native Wayland window cannot raise itself without an xdg-activation token, which the launcher cannot pass to the running editor. On 2026-11-23 (KDE Plasma 6.8.0, VS Code 1.140 as a native Wayland window) a click reached the helper (`ActionInvoked default` on the session bus) and the launcher exited 0, yet KWin left the window behind (the user's report in `/finish SUP33`; the KWin route decided without the user, its live checks in Limits). No activation token is requested. On macOS `terminal-notifier -execute "open -a <the .app bundle holding the editor> <folder>"`, or `open -b com.microsoft.VSCode` without a `product.json`; on Windows the toast's protocol launch `<urlProtocol>://file/<folder>`, on WSL `<urlProtocol>://vscode-remote/wsl+<distro><folder>`. The toast's XML is ASCII without quote marks (other characters as `&#N;`), since PowerShell also ends a single-quoted string at U+2018 to U+201B. The design follows public notifiers that open the folder to focus its window (`framerslab/claude-notify-hook`, `moozeeli/claude-notify`, `SeanTong11/wsl-tmux-notifier`; GitHub, read 2026-11-23 through search summaries only).
- **SessionEnd** (`reap.py --own`, matcher `prompt_input_exit|logout|other`, timeout 20 s, never `--scratchpads`): when a session exits it ends what its own Bash tool shells left running and what ended sessions left, and deletes stale test temporaries. It skips `clear` and `resume`, after which the session's work goes on. SessionEnd hooks share a 1.5 s budget, which a per-hook `timeout` raises up to 60 s (`CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS` overrides it). The 20 s cover the measured runtime (Benchmarks) plus reap's 5 s SIGTERM and 2 s SIGKILL waits. Hook commands carry `CLAUDE_PID` (Claude Code docs, environment variables), which `--own` uses to find its session. The command runs the project's own `reap.py`, and when that is missing (a worktree `/finish` removed, or one without the file) the main checkout's, found by cutting the nearest `/.claude/worktrees/…` from `CLAUDE_PROJECT_DIR` (`${d%/.claude/worktrees/*}`).
- **PreModelSwitch** (`harness.py hook`, no matcher, timeout 10 s; Claude Code v2.1.251 or later): `model_switch()` denies a `to_model` that is not a string whose base id (context suffix removed) is in the allowed set the model guard uses (`allowed()`), with the guard's HOW sentence as the reason. The hook checks `to_model` itself and registers without a matcher, since a target without a canonical name runs every hook whatever its matcher. An allowed switch gets no output, so Claude Code's own "Switch model?" confirmation, which names the warm cache it drops, is the only warning: the brief's warm-cache message was dropped (user decision 2026-11-23), because a hook's message shows only after the user has confirmed the switch. Like the rest of the guard it fails open on its own errors; the PreToolUse guard still refuses the next tool call of a session on an off-list model. `--selftest` requires the registration for every model (no matcher or `*`), since a narrowed matcher lets an off-list target with a canonical name skip the hook.
- **Push and submit guard** (user decision 2026-11-23): `.claude/githooks/pre-push` runs `shell.py push`, and `04-submit.py`'s `main()` calls `shell.py`'s `claude_shell()`. Both refuse when `CLAUDE_CODE_CHILD_SESSION=1` and `CP_USER` is not `1`. This closes `sh -c "git push"` and `g=git; $g push`, which `shell.py pre` let through. `CLAUDE_CODE_CHILD_SESSION` and not `CLAUDECODE` is the key, since IDE integrated terminals set `CLAUDECODE` too. A `!` command the user types shares the Bash tool's environment exactly: all 89 variables, compared by hash on 2026-11-22. So the user prefixes their own push or submission inside a session with `CP_USER=1` (`CLAUDE.md`, Git). `shell.py pre` now also runs for the Monitor tool, whose commands carry the same environment and pass Bash's permission rules; only Bash commands get its snapshot. It refuses any command whose text names `CP_USER`, `CLAUDE_CODE_CHILD_SESSION`, `--no-verify` or a value for `core.hooksPath` (`GUARD_TEXT`; reading the key stays allowed). The refusal covers any mention, a grep or a documentation edit included, and Claude handles such text with the Edit, Read and Grep tools (user decision 2026-11-23). The push commands printed for the user (`plan.py`'s claim line, `merge_pr.py`'s landing message, `/finish` step 7) read `CP_USER=1 git push …` (user decision 2026-11-23); the private sources repository's push needs no prefix, since its git directory sets no `core.hooksPath`. `pre`'s `git push` check skips the options of `env` and `sudo` (`env -u NAME`, `sudo -u root`), and `GUARD_TEXT` also refuses removing `core.hooksPath` (`--unset`, `unset`, `--remove-section core`) and `env -i` or `env -`, which would clear the environment the guards read. The deny reason points to the Read, Grep and Edit tools for such text.
- **Git's own files** (2026-11-23, closing a limit at the user's request; the text refusal's width decided without the user): `guard.py` refuses Edit, Write and NotebookEdit of any path whose resolved form passes through a `.git` file or folder in any case, in any repository, since `.git/config` names the hooks folder that guards pushes and commits. `GUARD_TEXT` also refuses a command naming `.git/config`, `.git/hooks` or a worktree's `config` under `.git/worktrees/` in any case, with repeated slashes or `/./`, and a git config include (`include.path`, `includeIf.`), which could point git at another config file. Like the rest of `GUARD_TEXT` it refuses a command that only mentions such a path; git commands that read or change the repository through git itself are unaffected.

### Ledger, Facts and Lab Log (SUP33)

- A `/finish` ledger `.claude/finish/<key>.txt` holds only rows `id | defect or decision | file:line | gap | source | state`: six `|`-separated non-empty fields, an id of letters, digits, `_`, `.` and `-` starting with a letter or digit, the kind `defect` or `decision`, and a state whose leading letters are `open` or `ask` (open) or `fixed` or `answered` (closed), in any case, so `open:` and `fixed.` count. Every other non-blank line is stray. `gaps.py`'s `ledger_rows()` decides this for both readers. Experiments go to the git-ignored `.claude/finish/<key>.lab.tsv`, one tab-separated row per attempt (date, ledger id, what was tried, result, `kept` or `rejected`, evidence path), and `/finish` (Ledger) says so. Reason: C03's ledger had reached 1,210 lines and 391 KB by 2026-11-22, of which 27 lines were rows; 1,146 non-blank lines were experiment notes.
- After a compaction `resume.py compact` re-injects only the open rows and says how many closed rows and stray lines it left out. The old pattern that also read `closed`, `done` and `dropped` as closed is gone: such a row is now stray.
- `gaps.py` writes every section of the facts in full (up to 400 lines each) to `.claude/finish/<key>.facts.txt` (plain text, since the validator reads every Markdown file) and prints the target, the role, the brief's first line with every `WARNING` and `STOP` line of it (step 1 acts on them), a line naming that file, and then whole sections in order of need: the ledger, the review record, the undecided optimization candidates, mutation records, agent-made omissions, open sweep rows, recorded limits, the comparison record, filed packages, TODO markers, branch changes, other worktrees, and the rest of the brief last, since `resume.py` re-injects the brief after a compaction and `plan.py show` reprints it (this order decided without the user). The ledger section starts with its stray-line warning and the count of closed rows, then as many open rows as fit; every other section prints at most 12 lines (`LINES`, decided without the user), then `... k more in the facts file`. A section that does not fit is named under `Not printed`. The printed text stays within the room `/finish`'s SKILL.md leaves (the next point), and at least 1,500 characters (decided without the user). The stray-line warning names the first ten line numbers and the lab file. The facts file is plain text (`.txt`, decided without the user). `/finish` step 7 deletes the lab log and facts file with the ledger.
- Room: after a compaction Claude Code re-attaches each invoked skill's first 5,000 tokens, its `!` output included, within 25,000 tokens for all skills (Claude Code docs, Skills, read 2026-11-23). This repository's Markdown takes about 2.5 characters per token: the evidence document's 27,919 characters added 11,165 input tokens to this session's next request, and 19 other tool results of 3,000 to 28,000 characters measured 1.0 to 2.5 (2026-11-23, this session's transcript usage). A delta also holds the call that produced the result, so the true figure for that document is at least 2.5 characters per token, and taking 2.5 errs toward a smaller room (decided without the user). So `REATTACH_CHARS` is 12,500 characters, and `/finish`'s SKILL.md (about 9,500 characters after this batch) leaves about 3,000 for printed facts.
- The review record `gaps.py --reviewed` writes for a batch without targets (SUP32, SUP33) covers the package's evidence and every file changed on the branch or uncommitted, except the plan files `plan.py` rewrites (`01-prompts.md`, `packages.json`, `batches.json`, `finish-log.tsv`; this list decided without the user) and `.claude/finish/` and `.claude/pause/`, so `/finish` audits any of them edited or newly changed after `/package`'s review (user decision 2026-11-23). Its facts read the package's evidence headings too. Before, such a record covered no file and was reused however the files changed.
- `03-consistency.py` lists in `skill_reattach` (a warning, not an error) each skill with a `!` line that leaves its printed output less than `MIN_FACTS` (2,500 characters, about 1,000 tokens), and each other skill above 90% of the 12,500 characters (both thresholds decided without the user): its body alone, since only `gaps.py` caps its output (user decision 2026-11-23). The `PostToolBatch` hook adds these warnings to the context after a batch that edited a skill's `SKILL.md`; they never fail it. It reads `gaps.py`'s three constants as literals and never runs it, since `/merge-pr` lists what the validator executes as code that runs on the host (`merge_pr.py`, `HOST_RUN`).

### Validator Cache (SUP33)

`03-consistency.py` reuses the mini-first check `full_only` (`05-extraction.py`'s `full_only_cached`) from the git-ignored `96-Local Testing/.extraction-cache.json` while all of its inputs are unchanged: the grab index records (which include the system headers' stamps), the bytes of every library header in the index's graph and of every found row's evidence document (or its absence), the found rows and their Operations cells, the Core full set, and the source of `05-extraction.py`, `10-grab.py` and the two modules grab loads (`_11_search.py`, `05-dependencies.py`). ### Memory Admission Gate (SUP33)

- `_00_memory_gate.py`'s `held(need, label)` wraps every `_00_memory_cap.supervise()`: testers, benchmarks, `02-integration.py`, `06-compare.py`, ad-hoc `_00_memory_cap.py -- <command>` runs, and the mutation campaign's baselines and stages. `06-compare.py` joined the cap module's entry points for this (`ENTRY_NAMES`; user decision 2026-11-23): its `ensure(mb=...)` had returned without a cap. The need is 11/10 of the peak `01-run.py` recorded for the entry and mode in `.run-stats.json`, plus 64 MB, the same reservation `01-run.py` schedules with. Without a record it is the cap. `--need N` and `ensure(need=...)` override it. The mutation campaign runs its own wrapper with `need=0` and takes the reservations in its own process: its cap for each stage's baseline, before the timed run, and for each stage part the shards it runs times the need of the baseline's scope (11/10 of the largest `MEMORY peak` its output prints, plus 64 MB, at most the per-test cap, else that cap), held for the whole part (one reservation per stage, decided without the user). Each test it starts passes `--need 0`, so no mutant queues while its timeout runs and no baseline's time includes the queue. Both reservations wait with the campaign's `--budget` deadline: one that passes in the queue stops the campaign as a budget stop. `06-compare.py` reserves only for `run`; `show` and `--help` need none. `05-extraction.py testers` copies `.run-stats.json` into its scratch tree, so each scratch tester reserves its recorded quick peak.
- Reservations: one JSON file per user (`$XDG_RUNTIME_DIR/cp-memory-gate.json`; `CP_MEMORY_GATE` names another, `0` turns the gate off), read and rewritten under an exclusive `flock`. An entry is a supervisor's pid and start time (a dead or reused pid drops out), its need, its state (`wait` or `run`), its label, its arrival time and its last poll (`beat`).
- Admission: the oldest live waiter (ties by pid; arrival order decided without the user) starts when MemAvailable, less what each running reservation may still grow into (its need minus what its run holds now: each capped `run-*.scope` below the reserving process once, never the scope that process runs in itself, plus the RSS of its other descendants), less its own need, leaves 2,048 MB (`CP_MEMORY_GATE_RESERVE_MB`), the headroom `01-run.py` and `04-mutation.py` keep (decided without the user). A run inside a running reservation of one of its ancestors does not queue, since an older waiter may wait for that very reservation, and a waiter whose last poll is 30 s older than the deciding one's (`STALE`; stopped or hung) holds no place (both decided without the user). It also starts, with a WARNING, when only its own ancestors run (they wait for it) or when no other gated run is running (waiting would free nothing). A waiter prints `WAIT` once and `ADMIT` with its time in the queue. It polls every second (`POLL`, decided without the user), refreshing its `beat`. An interrupt while queued removes its entry, and so does an error after the entry was saved; an unusable reservations file warns and runs without the gate.
- Inside one `01-run.py` the gate uses the same arithmetic as its scheduler where a peak is recorded: `01-run.py` starts suites whose reservations fit MemAvailable at its start less 2,048 MB (or its `--memory-mb`), and the gate admits them by the recorded peak too. They differ for a suite without a recorded peak, which `01-run.py` schedules at `CAP_MB` (4,096 MB) and the gate at the suite's own cap (8,192 MB for `02-integration.py`), and under `--memory-mb`; the gate then may hold a suite `01-run.py` started. No run compared them (design, not measured).

### SUP32 Follow-Ups (SUP33)

- `notify.py`'s title search stops while 3 s of the hook's shared 9 s deadline remain (`RESERVE`), so the fallback name's git calls and the notifier keep their time. The session is then named by its folder.
- `storage()` finds the editor's `storage.json` as VS Code 1.140 resolves its user data folder (its bundled `out/mainImpl.js`, read 2026-11-23): `$VSCODE_PORTABLE/user-data` for a portable installation, else `$VSCODE_APPDATA/<nameShort>`, else the platform's folder. On WSL it reads every Windows user's roaming folder, since the Windows editor's environment does not reach the distribution.
- A `.code-workspace` window (`workspaceIdentifier.configURIPath` in `windowsState`, the same source) contributes the folders its workspace file lists. The file is read as JSON with comments and trailing commas. A `path` entry is resolved against the file's folder and normalized, and a `uri` entry is converted like a window's folder. A missing or malformed workspace file skips that window only.
- `shell.py pre` also stores the value git reads for `core.hooksPath`. When `post` finds it changed and `/setup-check`'s `hook_check` says git no longer runs the main checkout's `.claude/githooks`, `post` blocks with the command the user types to restore it (`! git config core.hooksPath '<path>'`; Claude cannot run it, since `pre` refuses that text). A push in the same command has already run. `post` now also runs after failed Bash commands (`PostToolUseFailure`, matcher `Bash`; decided without the user), which can change files and the setting as well. Before this, a failing command escaped the protected-file and hooks checks. A live check on 2026-11-23 showed the failed command's snapshot consumed. The validator note in `post` names the event it ran for.

### Status Line and Agents

- The status line's cache part gains `miss N` from `prompt_cache.misses` once that is an integer above 0 (a bool shows nothing).
- `@researcher` sets `omitClaudeMd: true` (v2.1.271 or later): it starts without the user, project and local CLAUDE.md files, since its procedure and the delegation prompt name every file it reads. `@reviewer` and `@speedscout` keep CLAUDE.md for its scratchpad and memory rules. No agent sets `maxTurns`, since a cut review is worse than a long one.
- `@reviewer`'s report ends with a `Not verified` section listing each claim it could not check, with the reason, or `none`. `/package` (step 10) and `/finish` (step 2) say that a brief to `@reviewer` names what to review, never what not to flag. A cross-model reviewer waits until `finish-log.tsv` measures review yield.
- The `model:` pins of `/tidy`, `/duplicate-sweep`, `/omission-sweep` (Opus) and `/speed-sweep` (Fable) stay; `01-prompts.md` (Workflow) says to start each in a fresh session of the matching preset, since a skill whose model differs from the session's makes that turn re-read the whole context uncached.

Existing ledgers are not rewritten: C03's keeps its 1,146 stray lines until its next `/finish` moves them, which its facts now warn about. A run without a recorded peak reserves its whole cap, and one whose recorded peak is outdated reserves too little until `01-run.py` records it again. Without systemd scopes a reservation's current memory is the RSS of its process tree, which counts shared pages once per process. The arrival order holds a large run's turn, so smaller runs wait behind it. The gate is per user, not per machine.
- A capped scope's `memory.current` counts the page cache its processes filled (files a compile read or wrote), which the kernel can reclaim, so a running reservation's remaining growth is understated and the gate may admit more than its arithmetic intends; MemAvailable, which counts reclaimable cache as free, partly offsets this. The mutation campaign's stage reservation counts the RSS of its process tree, since its tests' scopes sit below its children.

- The gate's lock is a `flock` without a timeout: a gated run stopped (Ctrl-Z) inside the locked section, about 9 ms per poll, blocks every gated run of the user until it continues. After a suspend of the whole machine, the first waiter to poll finds the older ones stale and goes first. Gated runs nested under a running ancestor in two sessions at once (`01-run.py` and `05-extraction.py` start their children as new entry points) can each wait for the other's reservation until one finishes or times out. A scratch tester of `05-extraction.py testers` still counts its time in the queue against `--timeout`.
- In the main checkout, a support batch's review record also covers other packages' uncommitted files, so their edits reopen this batch's review.
- `shell.py post` sees a `core.hooksPath` change only when git reads it in this checkout (local, worktree, global or system configuration). A `GIT_CONFIG_*` variable set for one command lasts only that command and is refused by `pre`'s text check instead.
