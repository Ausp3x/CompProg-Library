### Hooks

- **PreCompact** (`resume.py precompact`, no matcher, timeout 60 s): stdout becomes instructions for the compaction summary, which Claude Code caps at 10,000 characters per hook; the script keeps under 9,000. It names the target (the batch or package id of the session's last typed `/package`, `/prune` or `/finish` call, else the branch or worktree name, through `gaps.py`'s `target()`), says which of the two named it (the typed command that gave the argument, cut to 80 characters so the later lines always fit), names the skill to resume and asks for its step number and the exact next step, gives the `/finish` ledger path (existing or not yet written; no line without a target or ledger) and the keep and drop lists of `CLAUDE.md` (Compact Instructions). It always exits 0: exit 2 would block the compaction, and a failure prints nothing. It shares `last_command()` and `ledgers()` with the `compact` SessionStart mode; `/pause` (`pause.py`) uses `last_command()` too.
- **Notification** (`notify.py`, matcher `permission_prompt|idle_prompt`, timeout 10 s): a notification titled `Claude Code · <name>` with the body `<why>[: <message>]`, where the name is the newest `custom-title` record in the transcript, read backwards in 1 MiB chunks (set by `--name` or `/rename`; Notification input carries no title) and otherwise the checkout folder with its branch, and the reason is "waits for your permission", "waits for your input" or "needs attention". The notifier is `notify-send --app-name=Claude Code` on Linux, `terminal-notifier` (else `osascript`'s `display notification`) on macOS, and a toast through `powershell.exe` with the Windows PowerShell app id on Windows and WSL (detected by `WSL_DISTRO_NAME` or a `microsoft` kernel release). It is silent when the notifier is missing, fails or hangs, and on malformed input; its git calls (2 s each) and the notifier (8 s) share a 9 s deadline inside the hook's 10 s; Claude Code ignores this hook's exit code. Claude Code fires these types only when the user seems away: `permission_prompt` after about six seconds without a keystroke, `idle_prompt` once `messageIdleNotifThresholdMs` (user scope in `~/.claude.json`, default 60000; the user set 30000 on this machine, user decision 2026-11-23) passes after a reply with no keypress, click or terminal focus change since it ended and no background agent running (Claude Code 2.1.330's code).
- **Click to Focus** (user decision 2026-11-23): in the terminal of VS Code or an editor built from it (`TERM_PROGRAM=vscode`: Insiders, VSCodium, Cursor) a click on the notification brings forward the editor window holding the session's folder. The editor is the one whose `product.json` sits four folders above its git extension's askpass script (`VSCODE_GIT_ASKPASS_MAIN`); its non-empty string keys `nameShort` (settings folder), `nameLong` (window title), `applicationName` (launcher) and `urlProtocol` (toast link) are used, and a key it lacks disables the step that needs it instead of falling back to VS Code's value, so a click never opens another editor. Without a readable `product.json` VS Code's values apply. The folder is the deepest window folder in that editor's `storage.json` (`windowsState`; Linux under `$XDG_CONFIG_HOME` or `~/.config`, macOS under `~/Library/Application Support`, Windows under `%APPDATA%`, WSL in every Windows user's roaming folder, keeping this distribution's `vscode-remote://wsl+<distro>` windows) containing the working directory, else the main checkout (`git rev-parse --git-common-dir`), so a linked worktree's session finds its checkout's window. Opening a folder that a window already holds focuses that window. On Linux, when `notify-send --help` lists `--action` (libnotify 0.7.10), the hook starts a helper in its own session and returns (without `CP_REAP_KEEP` since SUP34, so `/reap --own` and the SessionEnd hook end it): the helper shows the notification with a default action (`--action=default=Open`), waits up to 600 s, then sends SIGINT so that notify-send closes it, and on a click runs the launcher (from the editor's own `bin` folder, else `PATH`) on the folder. The launcher gets the hook's environment without the variables of the Claude Code session (`CLAUDE*`, `CP_USER`, `CP_REAP_KEEP`, `AI_AGENT`), inherited activation tokens and `VSCODE_*` other than `VSCODE_IPC_HOOK_CLI`, since a window it opens takes that environment. On KDE (`XDG_CURRENT_DESKTOP` lists `KDE`) the helper first has KWin activate the window: a one-shot KWin script, loaded, run and unloaded over D-Bus (`gdbus`, else `qdbus6` or `qdbus`), unminimizes and activates the first normal window whose title holds ` - <folder name> - ` and ends with the editor's `nameLong`, as VS Code's default `window.title` reads. It runs before the launcher, which took 1.1 s against 13 ms for the script. Reason: a native Wayland window cannot raise itself without an xdg-activation token, which the launcher cannot pass to the running editor. On 2026-11-23 (KDE Plasma 6.8.0, VS Code 1.140 as a native Wayland window) a click reached the helper (`ActionInvoked default` on the session bus) and the launcher exited 0, yet KWin left the window behind (the user's report in `/finish SUP33`; the KWin route a user decision 2026-11-24, its live checks in Limits). No activation token is requested. On macOS `terminal-notifier -execute "open -a <the .app bundle holding the editor> <folder>"`, or `open -b com.microsoft.VSCode` without a `product.json`; on Windows the toast's protocol launch `<urlProtocol>://file/<folder>`, on WSL `<urlProtocol>://vscode-remote/wsl+<distro><folder>`. The toast's XML is ASCII without quote marks (other characters as `&#N;`), since PowerShell also ends a single-quoted string at U+2018 to U+201B. The design follows public notifiers that open the folder to focus its window (`framerslab/claude-notify-hook`, `moozeeli/claude-notify`, `SeanTong11/wsl-tmux-notifier`; GitHub, read 2026-11-23 through search summaries only).
- **SessionEnd** (`reap.py --own`, matcher `prompt_input_exit|logout|other`, timeout 20 s, never `--scratchpads`): when a session exits it ends what its own Bash tool shells left running and what ended sessions left, and deletes stale test temporaries. It skips `clear` and `resume`, after which the session's work goes on. SessionEnd hooks share a 1.5 s budget, which a per-hook `timeout` raises up to 60 s (`CLAUDE_CODE_SESSIONEND_HOOKS_TIMEOUT_MS` overrides it). The 20 s cover the measured runtime (Benchmarks) plus reap's 5 s SIGTERM and 2 s SIGKILL waits. Hook commands carry `CLAUDE_PID` (Claude Code docs, environment variables), which `--own` uses to find its session. The command runs the project's own `reap.py`, and when that is missing (a worktree `/finish` removed, or one without the file) the main checkout's, found by cutting the nearest `/.claude/worktrees/…` from `CLAUDE_PROJECT_DIR` (`${d%/.claude/worktrees/*}`).
- **PreModelSwitch** (`harness.py hook`, no matcher, timeout 10 s; Claude Code v2.1.251 or later): `model_switch()` denies a `to_model` that is not a string whose base id (context suffix removed) is in the allowed set the model guard uses (`allowed()`), with the guard's HOW sentence as the reason. The hook checks `to_model` itself and registers without a matcher, since a target without a canonical name runs every hook whatever its matcher. An allowed switch gets no output, so Claude Code's own "Switch model?" confirmation, which names the warm cache it drops, is the only warning: the brief's warm-cache message was dropped (user decision 2026-11-23), because a hook's message shows only after the user has confirmed the switch. Like the rest of the guard it fails open on its own errors; the PreToolUse guard still refuses the next tool call of a session on an off-list model. `--selftest` requires the registration for every model (no matcher or `*`), since a narrowed matcher lets an off-list target with a canonical name skip the hook.
- **Push and Submit Guard** (user decision 2026-11-23): `.claude/githooks/pre-push` runs `shell.py push`, and `04-submit.py`'s `main()` calls `shell.py`'s `claude_shell()`. Both refuse when `CLAUDE_CODE_CHILD_SESSION=1` and `CP_USER` is not `1`. This closes `sh -c "git push"` and `g=git; $g push`, which `shell.py pre` let through. `CLAUDE_CODE_CHILD_SESSION` and not `CLAUDECODE` is the key, since IDE integrated terminals set `CLAUDECODE` too. A `!` command the user types shares the Bash tool's environment exactly: all 89 variables, compared by hash on 2026-11-22. So the user prefixes their own push or submission inside a session with `CP_USER=1` (`CLAUDE.md`, Git). `shell.py pre` now also runs for the Monitor tool, whose commands carry the same environment and pass Bash's permission rules; only Bash commands get its snapshot. It refuses any command whose text names `CP_USER`, `CLAUDE_CODE_CHILD_SESSION`, `--no-verify` or a value for `core.hooksPath` (`GUARD_TEXT`; reading the key stays allowed). The refusal covers any mention, a grep or a documentation edit included, and Claude handles such text with the Edit, Read and Grep tools (user decision 2026-11-23). The push commands printed for the user (`plan.py`'s claim line, `merge_pr.py`'s landing message, `/finish` step 7) read `CP_USER=1 git push …` (user decision 2026-11-23); the private sources repository's push needs no prefix, since its git directory sets no `core.hooksPath`. `pre`'s `git push` check skips the options of `env` and `sudo` (`env -u NAME`, `sudo -u root`), and `GUARD_TEXT` also refuses removing `core.hooksPath` (`--unset`, `unset`, `--remove-section core`) and `env -i` or `env -`, which would clear the environment the guards read. The deny reason points to the Read, Grep and Edit tools for such text.
- **Git's Own Files** (2026-11-23, closing a limit at the user's request; the text refusal's width a user decision 2026-11-24): `guard.py` refuses Edit, Write and NotebookEdit of any path whose resolved form passes through a `.git` file or folder in any case, in any repository, since `.git/config` names the hooks folder that guards pushes and commits. `GUARD_TEXT` also refuses a command naming `.git/config`, `.git/hooks` or a worktree's `config` under `.git/worktrees/` in any case, with repeated slashes or `/./`, and a git config include (`include.path`, `includeIf.`), which could point git at another config file. ### Ledger, Facts and Lab Log (SUP33)

- A `/finish` ledger `.claude/finish/<key>.txt` holds only rows `id | defect or decision | file:line | gap | source | state`: six `|`-separated non-empty fields, an id of letters, digits, `_`, `.` and `-` starting with a letter or digit, the kind `defect` or `decision`, and a state whose leading letters are `open` or `ask` (open) or `fixed` or `answered` (closed), in any case, so `open:` and `fixed.` count. Every other non-blank line is stray. `gaps.py`'s `ledger_rows()` decides this for both readers. Experiments go to the git-ignored `.claude/finish/<key>.lab.tsv`, one tab-separated row per attempt (date, ledger id, what was tried, result, `kept` or `rejected`, evidence path), and `/finish` (Ledger) says so. Reason: C03's ledger had reached 1,210 lines and 391 KB by 2026-11-22, of which 27 lines were rows; 1,146 non-blank lines were experiment notes.
- After a compaction `resume.py compact` re-injects only the open rows and says how many closed rows and stray lines it left out. The old pattern that also read `closed`, `done` and `dropped` as closed is gone: such a row is now stray.
- `gaps.py` writes every section of the facts in full (up to 400 lines each) to `.claude/finish/<key>.facts.txt` (plain text, since the validator reads every Markdown file) and prints the target, the role, the brief's first line with every `WARNING` and `STOP` line of it (step 1 acts on them), a line naming that file, and then whole sections in order of need: the ledger, the review record, the undecided limits, the follow-ups, the undecided optimization candidates, mutation records, agent-made omissions, open sweep rows, recorded limits, the comparison record, filed packages, TODO markers, branch changes, other worktrees, and the rest of the brief last, since `resume.py` re-injects the brief after a compaction and `plan.py show` reprints it (this order a user decision 2026-11-24). The ledger section starts with its stray-line warning and the count of closed rows, then as many open rows as fit; every other section prints at most 12 lines (`LINES`, user decision 2026-11-24), then `... k more in the facts file`. A section that does not fit is named under `Not printed`. The printed text stays within the room `/finish`'s SKILL.md leaves (the next point), and at least 1,500 characters (user decision 2026-11-24). The stray-line warning names the first ten line numbers and the lab file. The facts file is plain text (`.txt`, user decision 2026-11-24). `/finish` step 7 deletes every `.claude/finish/<key>.*` file with the ledger. The facts file also holds every section under an evidence heading `LIMIT_HEADING` matches (limits, handoffs, open items) in full, with no line cap; `/finish`'s report (step 9) lists each recorded limit in one line before its closing list (user decision 2026-11-24), since printing them all would push the ledger and `/finish`'s later steps out of the re-attached tokens.

### Memory Admission Gate (SUP33)

- `_00_memory_gate.py`'s `held(need, label)` wraps every `_00_memory_cap.supervise()`: testers, benchmarks, `02-integration.py`, `06-compare.py`, ad-hoc `_00_memory_cap.py -- <command>` runs, and the mutation campaign's baselines and stages. `06-compare.py` joined the cap module's entry points for this (`ENTRY_NAMES`; user decision 2026-11-23): its `ensure(mb=...)` had returned without a cap. The need is 11/10 of the peak recorded for the entry and mode in `.run-stats.json` (by `01-run.py`, and since SUP34 by every passing tester and benchmark), plus 64 MB, the same reservation `01-run.py` schedules with. Without a record it is the cap. `--need N` and `ensure(need=...)` override it. The mutation campaign runs its own wrapper with `need=0` and takes the reservations in its own process: its cap for each stage's baseline, before the timed run, and for each stage part the shards it runs times the need of the baseline's scope (11/10 of the largest `MEMORY peak` its output prints, plus 64 MB, at most the per-test cap, else that cap), held for the whole part (one reservation per stage, user decision 2026-11-24). Each test it starts passes `--need 0`, so no mutant queues while its timeout runs and no baseline's time includes the queue. Both reservations wait with the campaign's `--budget` deadline: one that passes in the queue stops the campaign as a budget stop. `06-compare.py` reserves only for `run`; `show` and `--help` need none. `05-extraction.py testers` copies `.run-stats.json` into its scratch tree, so each scratch tester reserves its recorded quick peak.
- Reservations: one JSON file per user (`$XDG_RUNTIME_DIR/cp-memory-gate.json`; `CP_MEMORY_GATE` names another, `0` turns the gate off), read and rewritten under an exclusive `flock`. An entry is a supervisor's pid and start time (a dead or reused pid drops out), its need, its state (`wait` or `run`), its label, its arrival time and its last poll (`beat`).
- Admission: the oldest live waiter (ties by pid; arrival order a user decision 2026-11-24) starts when MemAvailable, less what each running reservation may still grow into (its need minus what its run holds now: each capped `run-*.scope` below the reserving process once, never the scope that process runs in itself, plus the PSS of its other descendants; RSS before SUP34), less its own need, leaves 2,048 MB (`CP_MEMORY_GATE_RESERVE_MB`), the headroom `01-run.py` and `04-mutation.py` keep (user decision 2026-11-24). A run inside a running reservation of one of its ancestors does not queue behind other waiters but needs its whole need beside that reservation (SUP34 review: a recorded peak covers only the reserving run's own scope, so drawing from the ancestor's unused part, as SUP34 first did, admitted runs that did not fit); when it does not fit and every running reservation has a live queued run below it, the oldest such nested waiter starts with a WARNING, so two sessions' nested runs no longer wait on each other (SUP34; kept by user decision 2026-11-24, chosen over a child that never queues, which would skip the memory check). A waiter whose last poll is 30 s older than the deciding one's (`STALE`; stopped or hung) holds no place (user decision 2026-11-24). It also starts, with a WARNING, when only its own ancestors run (they wait for it) or when no other gated run is running (waiting would free nothing). A waiter prints `WAIT` once and `ADMIT` with its time in the queue. It polls every second (`POLL`, user decision 2026-11-24), refreshing its `beat`. An interrupt while queued removes its entry, and so does an error after the entry was saved; an unusable reservations file warns and runs without the gate.
- Inside one `01-run.py` the gate and the scheduler reserve the same need for each suite, both through `need_of()` (one formula since 2026-11-25; before, `01-run.py`'s copy lacked the cap): 11/10 of the recorded peak plus 64 MB, at most the cap, else the cap, which is `CAP_MB` (4,096 MB, or `CP_TEST_MEMORY_MB`) for every suite it starts, none of which sets its own. `01-run.py` starts suites whose reservations fit MemAvailable at its start less 2,048 MB (or its `--memory-mb` budget), and the gate admits each by MemAvailable when it starts, so another session's runs, or a `--memory-mb` above what is free, can still make the gate hold a suite `01-run.py` started.

### Memory Admission Gate (SUP34)

User decisions 2026-11-23; backfill's rule user decision 2026-11-24.

- A running reservation's current memory excludes what the kernel can reclaim: a capped scope counts `memory.current` less `memory.stat`'s `file` without its `shmem` (tmpfs files, `/tmp`'s here, stay in memory; fixed in review), never below 0, and a process outside a scope counts its PSS (`smaps_rollup`), else its RSS when that file is unreadable or empty. A descendant holding its own running reservation counts under that reservation, with its subtree, not under its ancestor's too (fixed in review).
- Peaks: `supervise()` of a tester or benchmark that reserved its recorded need records `[max(pre-flight peak, main peak), seconds]` under its `.run-stats.json` key (`<mode> <path>`, or `run <path>` for a benchmark, which has no mode; fixed in review) after a passing run (the main scope's peak reaches it through a temporary `cp-peak-*` file named in `CP_MEMORY_PEAK`, which `/reap` deletes when a killed run leaves it). A record is `[peak, seconds, runs]`: the last three runs' pairs, and their maxima before them (user decision 2026-11-24, after `/finish SUP34`; before, a direct run only raised a record and `01-run.py` replaced it). So a suite that got lighter lowers its record after three runs, while one light, partial or warm-cache run cannot; an older two-element record counts as one run. `01-run.py` adds a run for every suite that passed, marks the suites it starts with `CP_RUN_STATS_OWNER` so they do not record twice (they still reserve with their recorded seconds, fixed in review). An entry point without a key, which records nothing, reserves its cap and reads no record. All writers merge under `.run-stats.json.lock`. `CP_RUN_STATS` points every reader and writer at another file, keys still relative to `96-Local Testing`; `05-runner_tester.py`'s real tester runs use it, so they never touch the real file (2026-11-25, user decision 2026-11-24). `02-integration.py` and `06-compare.py run` reserve and record under their key followed by what their peaks depend on (`ensure(variant=...)`, user decision 2026-11-24, `/finish SUP34`): `--jobs N`, `--sanitizers` and the compiler command for the integration build (`run 02-integration.py --jobs 16 g++`), and the rig, `--compilers` and `--gate` for a comparison, since its builder runs at most three builds at once whatever the sides; an unrecorded variant reserves the cap, and their options are parsed before the cap, so a bad one exits uncapped. Seconds count from admission and include the pre-flight; `01-run.py` subtracts the queue time each suite prints in its own `ADMIT <tester file>: after N s in the memory queue` line (a nested run's line, which waits inside the suite's reservation, is not subtracted), so its records leave it out too (fixed in `/finish SUP34`, user decision 2026-11-24).
- Lock: `flock` is tried every 5 ms for at most `LOCK_WAIT` = 10 s; past it the run warns and runs without the gate, its releases try the lock once, and `remember()` merges without it (kept by user decision 2026-11-24; a blocking lock with SIGALRM works only in the main thread).
