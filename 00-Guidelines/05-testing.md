# Library Tests and Benchmarks

`96-Local Testing` verifies library files. `09-Contest Testing` compares problem solutions.

## Layout and Modes

- Mirror the library path: `96-Local Testing/02-Data Structures/01-dsu_tester.py` with helper `.cpp` files beside it. One Python entry per header or module; shared infrastructure in `_00_cpp_test_runner.py` (the `Builder` every C++ test build goes through, `Docs/00-parallel.md`; `03-consistency.py` rejects a library tester or runner (`01`–`07`) that runs the compiler directly, `-fsyntax-only` checks and compiler queries apart) and, for `02`–`07`, `_00_contest_runner.py`, whose per-suite differences are parameters. Tests include the real header and run from any working directory; build outputs go to a temporary directory.
- Modes: `quick` (smoke subset, seconds), `full` (every operation and configuration), `stress` (extended random, exhaustive and adversarial, seeded, with `--rounds`). Document the actual coverage of each mode; never label a truncated run `full`. A full or stress run's `PREFLIGHT ... quick passed` line is its quick run (Memory Safety); never run quick separately before it.
- Quick bound (user decision 2026-11-08): each build's quick run takes at most 10 s alone on the reference machine (i9-11900H), compile time apart. Over it, first find a cheaper oracle with the same checks, then smaller quick-mode inputs; full and stress inputs and oracles stay unchanged, and a check that fits only in full moves there. The runners print `TIMING <build> mode=<mode> compile=<s>s run=<s>s` per build, and `01-run.py` lists the quick builds over 10 s as a NOTE in every mode (a full or stress run from its pre-flight), never a failure, since it times them beside other suites (Benchmarks: no fixed timing gates across machines).
- `01-run.py` discovers testers by glob; quick mode runs every folder except `01-Core`, whose quick testers are listed in `QUICK`. It and `02-integration.py` run their jobs in parallel: a job that fails beside others reruns alone, and only a failure alone counts. `01-run.py` ends with a NOTE naming each suite that passed only on its rerun and each command over half its limit: a passing exit code does not clear either, and a package fixes them with a cheaper oracle with the same checks, or else a raised limit with its measured reason. A tester writes only to per-process temporary paths, since stress mode runs it concurrently with several seeds.
- On headers whose row and owning package are both `verified`, `03-consistency.py` enforces the `03-cpp.md` closing-brace rule and, on type headers, the type-header rule, plus the brace rule on their C++ testers and benchmarks, ignoring comments, literals, preprocessor lines and initializer braces. While editing, `python3 '96-Local Testing/03-consistency.py' --braces <files>` checks any files for the brace rule, the comment cap and, on `01-Core` and `02-Data Structures` type headers, the type-header rule. Outside the maintainer's main checkout (a linked worktree, or a clone whose `compprog.role` is not `maintainer`, CI included), ledger records of git-ignored artifacts (archive binaries and caches, benchmark logs) pass when the file is absent, so a fresh worktree or clone validates without them; the maintainer's main checkout keeps requiring them (user decision 2026-11-16).
- Output: named tests, in-place progress on a terminal, plain lines when redirected, green PASS and red FAIL, nonzero exit on failure, explicit SKIP for missing hardware or interpreters. A failure prints seed, smallest known reproducer, operation and input, expected and actual values, configuration, command, and timeout or crash details. Failures must survive `-DNDEBUG`; never use a removable `assert` as the only oracle. Never ignore a subprocess failure.

## Memory Safety

- Every tester, benchmark driver, `02-integration.py` and `06-compare.py` calls `_00_memory_cap.ensure()` at start (the shared runners do it on import; `03-consistency.py` rejects an entry point that does not). It runs the entry point in a transient systemd user scope capped at 4096 MB by default (`CP_TEST_MEMORY_MB` overrides) with swap off, where only a runaway process is killed and the runner reports it as a FAIL. A suite that legitimately needs more memory passes `ensure(mb=...)` and records the reason and measured peak in its evidence.
- Before its scope starts, every run through `supervise()` (an entry point's `ensure()`, the `_00_memory_cap.py` command line) waits in the memory admission gate (`_00_memory_gate.py`, SUP33) until MemAvailable, less what the gated runs already running may still grow into, covers its expected peak with 2048 MB to spare: the peak `01-run.py` recorded for the entry and mode in `.run-stats.json`, else its cap (`--need` or `ensure(need=...)` override it, `0` for a wrapper whose heavy children gate themselves or that holds their reservation itself, as `04-mutation.py` does). Runs of every session queue in arrival order; one prints `WAIT`, then `ADMIT` when it starts.
- Full and stress runs first rerun the entry point in quick mode under a 2048 MB pre-flight cap (`CP_TEST_PREFLIGHT_MB`) and start only if it passes; `CP_TEST_PREFLIGHT=0` skips the pre-flight for a deliberate rerun.
- Each capped run ends with `MEMORY peak=... cap=... oom_kills=...`; evidence records the full and stress peaks.
- A suite's builds compile and run at once, at most three within its cap (`Builder.build_all`, `Builder.concurrently`), each reserving its measured peak; stress mode runs them one at a time, its peaks being unmeasured, and `_00_foundation_runner.py` runs its few seconds of tests in order. A contest suite passes `memory=` to `main` when one build, compile or run, needs over 1200 MB; a NOTE at 90% of the cap and the failure of a build the cap killed name that parameter. Run at most six heavy compiles (Core full headers, their testers and drivers) at once, fewer beside a running tester or agent. One `_00_memory_cap.py` cap covers its whole process tree (about four `-O2 -g` builds per 6–8 GB), and a build the OOM killer ends leaves no binary, so check each exists before running it.
- A scope ends with its supervisor however the supervisor dies, a caller's timeout SIGKILL included (`lead()`), so a scratch driver never outlives the command that ran it; what still escapes, and the temporaries a killed run leaves in `/tmp`, `/reap` clears (user decision 2026-11-16).
- Ad-hoc probes, scratch binaries and one-off benchmarks run through `python3 '96-Local Testing/_00_memory_cap.py' [--mb N] -- <command>`; never run a compiled test program uncapped.
- Inputs given to an optimized (`-DNDEBUG`) build stay inside every documented domain; only the checked build's `--invalid` probes violate preconditions.

## Coverage

- Keep a feature-to-test map in the evidence document: every operation in the inventory row maps to at least one test.
- Call every operation as user code does: `friend` functions unqualified through ADL, `static` builders as `Type<T>::name`, companion functions as `TypeCompanion::name`.
- Before a same-context form or second implementation (`03-cpp.md`, One API per Operation) is deleted, its test cases are reproduced against the kept operation and mapped in the feature-to-test map.
- Oracles in priority order: independent brute force, bounded exhaustive small domains, algebraic or metamorphic identities, deterministic seeded random stress, saved regressions. Agreement between full and mini or between C++ and Python is supporting evidence only, never the sole oracle. Validate the brute force itself.
- A contest operation generic over a Core type runs its cases with the mini default and with the full type. A slower algorithm and its faster counterpart check each other on their shared domain, and each keeps an independent oracle of its own.
- Cases: empty and singleton, boundaries of every documented domain, extreme magnitudes, zero and negative values, duplicates and degeneracies, disconnected graphs, self-loops and multi-edges where allowed, threshold and alignment neighbours, aliasing of inputs and outputs, repeated calls, reset and cache changes, valid no-answer inputs, and each documented precondition failure under a checked build.
- Builds: optimized GNU++20, sanitized (`-g -fsanitize=address,undefined`; the contest runner's `ASan-UBSan`, at `-O1`), `-DNDEBUG`, `LOCAL` and non-`LOCAL` when behavior differs; header alone, `98-basic`, `99-all`, mixed full and mini, two translation units; scalar and each ISA path with an explicit SKIP where the CPU lacks it; the C++ path beside inline assembly through constant evaluation on the run-time test's inputs; a contest suite whose results depend on floating-point contraction passes `native=True` to the contest runner for an optimized `-march=native` build in full and stress mode, as AtCoder compiles, with a SKIP where the CPU lacks FMA (user decision 2026-11-13); CPython and PyPy for Python. Every package also runs its suites in `full` mode with `CXX=g++-14` (the runners read `CXX`) as the floor check and records the result in its evidence. Every contest suite compiles with `-Wall -Wextra -Wconversion -Werror` (`_00_contest_runner.py`); elsewhere use `-Wall -Wextra -Wconversion`, and a warning is acceptable only when the bound is stated in the code. The contest runner's `checked` build (debug containers or assertions, no sanitizer) is `-O0` in quick mode, so every suite still runs unoptimized, and `-O1` in full and stress.
- A package that changes a header also runs `python3 '96-Local Testing/02-integration.py'` before it is verified, adding `--sanitizers` when an `01-Core` header changed.
- Approximate comparisons use justified absolute or relative tolerances; never compare exact big integers through floats.

## Mutation Testing

- Every header a package adds or changes, Core full included, gets a campaign once its tests pass: `python3 '96-Local Testing/04-mutation.py' run <header>`. It mutates scratch copies of the working tree with mewt (pinned and installed by `04-mutation.py install`, a required tool of `/setup-check`) and escalates each mutant through the tester's quick mode and full mode on the optimized build, then full mode on the builds not yet run in full (a Core tester, which has no build option, runs quick then full, making each build when it first runs it and stopping at the first failure, user decision 2026-11-17), so a survivor has passed every configuration in full mode. Without mewt it prints SKIP and leaves no record. One campaign runs per machine; a second waits for it (user decision 2026-11-04). Procedure, costs and limits: `96-Local Testing/Docs/00-mutation.md`.
- Scope (user decision 2026-11-03): a header whose evidence document holds a record is mutated only on the lines changed since the recorded blob, a header without one on every line. Every whole-file campaign, Core full included, tests a seeded sample of at most 250 mutants: 125 of high severity, 75 medium and 50 low, each class drawn uniformly, a share a class cannot fill passing to the next class and what the last leaves going back to the first that holds more (user decision 2026-11-20, replacing the earlier sample rules recorded in `10-decisions.md`). A diff-scoped campaign tests every mutant of its lines. `--whole`, `--severity` and `--sample` override, and the record states the scope and sample. A run the `--budget` stopped is incomplete: resume it with the same `--workdir`.
- Each mutant's test runs in its own memory-capped scope, so a runaway mutant dies alone. A kill at that cap (three times the baseline's peak, at least 1024 MB, at most the tester's own cap) counts as caught, and so does a timeout (three times the stage baseline, at least 60 s) that recurs when the mutant is retested with its own CPU cores, since contention among concurrent tests can slow a survivor (user decisions 2026-11-04, 2026-11-09). Close each survivor with a test, then rerun with the same `--workdir`, which retests the survivors with the current tester; otherwise record it as equivalent after the five checks of the Trail of Bits procedure (type context, reachability, downstream use, semantic comparison, distinguishing input). A mutant equivalent only because the contract leaves the changed state unspecified needs the user's decision; one that differs only under `NDEBUG` past a violated precondition and still ends within the operation's bound is equivalent (user decision 2026-11-12). A mutant with identical results whose only effect is work above the stated bound but under the timeout is recorded as runtime only, with its work argument and measured ratio (user decision 2026-11-14).
- The header's evidence document keeps one `## Mutation Testing` section in one shape (user decision 2026-11-22): the current `Record:` line the run prints (it names the header's git blob) with its stage times; one table of the open survivors at current line numbers, each with its argument (equivalent or runtime only); earlier campaigns cited in one clause, without hashes or stage times. Closed, caught and removed survivors are deleted. A survivor whose argument is still needed, on lines a newer diff-scoped record did not cover, stays in the table and names the record it came from in one clause. `04-mutation.py check` passes only while the record names the current blob and leaves 0 untested; a completed run stores the blob in git's object database so a later run can diff against it.
- Later passes (user decisions 2026-11-03 and 2026-11-04): `/finish` reruns the campaign on the lines its own fixes changed and reviews the survivors with its fix diff. `/prune`, `/restyle` and a `/package` call-site migration in another package's header rerun it on their changed lines only for a header that already holds a record; a header without one needs none from them, and the checks pass it (`check --existing`): `/finish` for headers whose evidence document another package lists and the package itself does not, `/merge-pr` for those and for every header that only `/prune` or `/restyle` commits changed. `/merge-pr` otherwise only checks.

## Extraction

- `python3 '96-Local Testing/05-extraction.py'` checks `09-Contest Testing/10-grab.py` on the library: `ops` extracts every operation of every implemented `01`–`07` row alone (`Type::member` for a struct's operation) and compiles it with `-fsyntax-only` after the template and debug headers on `$CXX` and `g++-14`, instantiating each class or function template it reaches with the first candidate arguments (`lng`, the `Sum` and `RangeAddRangeSum` presets, `ulng`; `4`; `false`) that compile after the whole header, fails on an extraction keeping code outside its header's include closure, and on a public function template whose type parameter grab must infer for want of the default `03-cpp.md` (Headers) asks for (pending outside verified rows); `testers` runs each C++ tester's quick mode in a scratch tree where every library header but the template and debug headers keeps only its quoted includes and its lines of the declarations the tester's files name from their include closures, so C++ a tester writes itself extracts too. `--mode quick` samples rows and testers; `full` takes all. Without libclang it prints SKIP. Evidence: `96-Local Testing/Docs/00-extraction.md`.
- A package that adds or changes a header also runs `05-extraction.py ops --filter <header>` and, for a C++ tester, `05-extraction.py testers --filter <tester>`, and records both in the header's evidence, so a form grab mishandles fails with the package that brings it (user decision 2026-11-07).
- Mini first (`03-cpp.md`, Core type parameters): `03-consistency.py` rejects a contest template default naming a Core full type, a mini row that lacks an operation of its full row (beside `internals:` and `missing:`) and an operation whose default form extracts a Core full header that is not scalar without a `full-only until` line in its evidence document naming it in a code span. The last check reads the cached grab index only, on the rows whose include closure is indexed, and reports how many rows wait; `05-extraction.py ops` always runs it. Findings on support targets of open 2026-11-05 batches and on rows or packages not yet verified are listed in `mini_first_pending` instead of failing.

## Benchmarks

- Benchmarks are separate from correctness. Record CPU, compiler and flags, interpreter, input sizes and distributions, seeds, warmup and repetition counts, medians, memory, and the compared implementation. Verify outputs inside the benchmark so the work cannot be optimized away.
- Drivers are `<NN-name>_benchmark.py/.cpp` beside the tester (`00-<stem>_benchmark.*` for a folder-wide driver). Raw logs `*_benchmark.json`/`.jsonl` are written beside the driver and are ignored by git; commit only the summary table with conditions and medians in the header's evidence document.
- Cover small, typical, large and adversarial inputs and every dispatch threshold. The Barrett/Montgomery 20% rule from principles applies outside Core. No fixed timing gates across machines.
- A speed change is adopted only on A/B evidence against the previous header in the ISA and scalar builds on the deciding compiler, the newest GCC a target judge runs (`03-cpp.md`, Toolchain and Judges; `g++-15` today): cycle and instruction counts (`perf stat` or perf_event_open counters), since wall-clock varies by about 10% here. The machine runs nothing else meanwhile: a build, a test or the validator an edit starts disturbs the counters. Reject a difference within noise, rule out layout effects with `-falign-functions=64 -falign-loops=32`, time a branchy kernel over a pool of random operands (one repeated pair trains the branch predictor), and re-measure a remaining gap on the final header before fixing it. The finished header is compared once more against the previous header on the floor compiler, on the local `g++` and in an `-O2 -march=native` build on the deciding compiler, as AtCoder compiles (this machine's instruction set stands in for AtCoder's unknown CPU); a row more than 3% slower in one of them is a losing row (user decisions 2026-11-17, 2026-11-18). `96-Local Testing/06-compare.py` runs both comparisons from the header's `<NN-name>_compare.cpp` rig and prints the `Comparison:` line the evidence records (`96-Local Testing/Docs/00-compare.md`). Allocation, alignment and page-size changes stay judge-unverified until the user's submissions confirm them: local counters cannot see the judge's caches (Zen 3, 512 KB L2).
- Optimization candidates (Core full; `01-principles.md`, Profiles): the header's evidence document keeps `### Optimization Candidates` under `## Benchmarks`, a table `Operation | Candidate | Verdict | Evidence` that names every operation of the inventory row. Candidates come from every place that can name one: the catalogs and judge leaders (`@researcher`, `@speedscout`), review limits, earlier evidence and History, a profile of each recorded benchmark, and a walk over each operation through these classes: another algorithm; another reducer or representation per modulus or size class; a branch against a select; a compile-time or cached constant; a dispatch threshold; an ISA kernel; independent chains in place of one dependent chain; inlining and code placement; allocation; parsing and formatting. A verdict is `adopted` or `rejected` by the A/B rule above, its Evidence cell naming the compiler (`GCC 15`), and one measured on another compiler than the deciding one is undecided; `rejected` on one of three arguments, written `argument:` and never a predicted cost (user decision 2026-11-18: outside the ISA set, a contract change the user declined, the adopted form's own operations plus more on every input); or `other owner` with the numbers handed to that package's note. An operation the walk leaves empty gets one row, `none found`, naming what was examined. A loss a stage leaves against the previous header is a candidate too: it is removed, shown to lie outside the source (the same instructions under another code placement), or kept as a trade-off under the next rule.
- Mixed rows (user decision 2026-11-17): a candidate that wins some rows and loses others is first separated: when something the library can see (a modulus or value class, the word size, a length, a flag cached with the modulus) splits the winners from the losers, the header dispatches on it and nothing loses. Where only the caller's data decides, take each form's worst slowdown against the other over all rows and builds and adopt the form whose worst is smaller; when the two worst cases are within 5% of each other, the better geometric mean decides. Every row left more than 3% slower than the previous header is recorded in the evidence as a trade-off (the rows that lose, the rows that win, the date) and reported at `/finish`. The user is asked before adoption only when the two worst cases are within 5% or a losing row is a headline row, one of the operations and types most contest code uses, which the evidence document names.
- Other CPUs (user decisions 2026-11-17, 2026-11-19): the counters are this machine's. A candidate that removes instructions, mispredicted branches or steps of a dependent chain is adopted on them, since that carries to any x86 CPU. A candidate that wins only in cycles (latency or port use) is also run through `llvm-mca` on its kernel with `-mcpu=znver3`, `-mcpu=znver4` and `-mcpu=skylake` (the class of the CPU reported for Codeforces, `03-cpp.md`, Toolchain and Judges); when a model shows no gain, it goes to the user as a trade-off, and when one shows a loss, the Mixed rows comparison of worst cases counts the modeled CPUs too (hardware division lost that way in `05-modint.hpp`: 80 against 31 cycles a step on the Skylake model). A threshold is recorded with the CPU it was tuned on, and only the maintainer's submissions confirm a judge.
- An optimization sweep of a Core full header (user decisions 2026-11-17) follows these rules:
  - Order: the Core full headers whose hot code it calls are swept first.
  - Matrix first: before a candidate is timed, the benchmark holds a row for every operation on every dispatch class (modulus or value class, word size, length range), with predictable, random and worst-case data, in a dependent chain and as independent calls; for data beyond a few kilobytes it holds sizes on both sides of each cache level and records cache misses, and a lookup table of that size has a row that evicts it between calls.
  - Budget: each row states its expected cost in basic operations (multiplications, divisions, mispredicted branches and cache misses per element or call); a measured cost more than 10% above it is a candidate.
  - Generated code: the compiled code and counters of every hot kernel are read on the deciding compiler, and what they show (a jump where a select was meant or the reverse, a call that was meant to be inlined, a redundant move or extension, a loop left scalar) is a candidate.
  - Final set (user decision 2026-11-18): before the header is written, each adopted candidate is timed removed alone from the full adopted set and each threshold against its neighbouring values; a piece that no longer wins is dropped, and a candidate adopted afterwards is timed against that set.
  - Judge leaders: a header with a Library Checker problem is marked `verified` only after `/speed-sweep` has compared it with the fastest submissions and every difference it lists is in the table.
  - Cleanup (user decision 2026-11-18): a prototype with one switch per candidate stays in the scratchpad. The installed header has every switch resolved to its verdict and repeated code merged (`03-cpp.md`, Style), and is accepted only when every row of the comparison driver keeps its checksum and its instruction count against the build before the cleanup; a row that differs is explained or the cleanup step is undone.
  - Stop: the sweep ends when one full pass over the finished header (generated code, budgets, `@reviewer`) names no new candidate.
  - Stale evidence: the evidence records the compiler versions and the blobs of the Core headers the benchmark includes; when the deciding compiler or the hot code of one of those headers changes, the comparison is rerun before the next status claim (`/finish` reports a stale `Comparison:` line).
- A Core mini records its scaling (n, 2n and 4n against its complexity) and its speed ratio to the full type built without ISA flags. After its full type's sweep the ratio is recorded again and `/finish` lists each scalar win the mini lacks with its gain and its cost in lines; the user chooses which the mini takes (user decision 2026-11-18).
