## 1. DioSolution.g is 0 on no solution, but the evidence contract says g = gcd(|a|,|b|) with no exception

- **Kind:** correctness
- **Location:** `05-Mathematics/03-equation_solvers.hpp:18`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** Low severity: this is a contract mismatch, not wrong arithmetic. In the solveDioEq row of 05-Mathematics/92-equations.md, `g=gcd(abs(a),abs(b))` is stated for every result. When the equation has no solution, line 18 does `if (c % g != 0) { return {}; }`, so the caller gets g = 0 even though the gcd was just computed and is nonzero. The header comment (lines 5-6) never says what g means, or that it is 0 when dimension is -1. 03-cpp.md asks for the meaning of results to be documented in the comment above each struct or function. The C++ tester only checks s.g when a solution exists (tester line 23), and the Python oracle hard-codes g = 0 for the no-solution case, so the tests lock in the undocumented behavior. Fix, either way: (a) return the gcd with `return {-1, 0, 0, 0, 0, g};` and update the oracle's no-solution tuple, or (b) document in the header and in 92-equations.md that g is 0 when dimension is -1. Option (a) costs nothing and gives the caller more information.
- **Repro:** solveDioEq(2, 4, 1) returns dimension = -1, g = 0. gcd(2, 4) = 2, which is what the 92-equations.md contract `g=gcd(abs(a),abs(b))` says g should be. Checked with a probe in /tmp/p012rev.cpp, which printed `-1 0 | 1 2` for (2,4,1) and (2,4,2).

## 2. Odd and Wheel30 are 3-6x slower than Plain at high endpoints because of branchy per-prime start offsets

- **Kind:** optimality
- **Location:** `05-Mathematics/06-segmentedsieve.hpp:40`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** Every block rescans every base prime with p*p < hi, so at high endpoints the per-prime start computation dominates. Odd adds `if (odd && !(start & 1)) { start += p; }` (lines 44-45), whose branch is mispredicted about half the time; Wheel30 adds `while (!(MASK >> (k % 30) & 1)) { ++k; }` (lines 39-40), which runs 0-5 times unpredictably. Branch-free fix with identical results: for odd p, `lng k = max(p, first / p + (first % p != 0)); if (odd) { k |= 1; } lll start = lll(p) * k;` (p*k is odd iff k is odd), and for Wheel30 a 30-entry next-coprime-residue table `k += NEXT[k % 30];`. Measured on [1e16-1e5, 1e16), block 32768 (reviewer / three skeptics): original Plain 60-82 ms, Odd 189-242 ms, Wheel30 310-418 ms; patched Plain 58-80, Odd 58-76, Wheel30 60-83. On [1e12-2e6, 1e12) original 30/46/72 ms, patched 29/20/23 ms; on [0, 1e8] no regression (patched 531/225/287 vs 534/232/308). 116,640 differential cases (exhaustive l in [-5, 200] with blocks 1, 2, 7, 30, 31 plus 3000 random intervals up to 5e6, all modes) gave 0 mismatches. The evidence 05-Mathematics/95-segmentedsieve.md (lines 25 and 87) wrongly attributes the gap to an expected per-block/base-scan tradeoff; correct it with the code.
- **Repro:** Reviewer probes /tmp/ssprobe/p.cpp (timing) and /tmp/ssprobe/c.cpp (differential); skeptic probes /tmp/skeptic{1,2,3}/. g++ -std=gnu++20 -O2; SegmentedSieveBase(1e16-1) then forEachPrime on [1e16-1e5, 1e16) with block 32768 in each mode.

## 3. Materialized sieve built from a shared base copies all base primes, contradicting its M bound

- **Kind:** optimality
- **Location:** `05-Mathematics/06-segmentedsieve.hpp:115`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** `bprms = base.bprms;` in the reuse-base constructor, `reset` and `fromClosed(..., base)` copies all pi(sqrt(base.max_value)) primes in time and memory, but nothing reads a prime with p*p >= r (`forEachFactor` stops at line 128, `getPrimeFac(x)` at line 147). The struct comment (lines 91-92) claims `M: O(n + pi(sqrt(R)))` and the setup cost leaves out the copy. Fix: copy only the needed prefix, e.g. `bprms.assign(base.bprms.begin(), upper_bound(base.bprms.begin(), base.bprms.end(), segmented_sieve_detail::root(max(lng(0), r - 1))));`, or, if the full copy is intentional, change the comment to O(n + pi(sqrt(base.max_value))).
- **Repro:** Build SegmentedSieveBase(1e16-1), then 100 objects SegmentedSieve(100+q, 200+q, base): 510-627 ms total, each storing 5,761,455 primes (46 MB) where 4 are needed; with their own small base the same 100 objects take 0.04 ms.
