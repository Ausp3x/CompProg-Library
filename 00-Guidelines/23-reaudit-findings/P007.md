## 1. Inventory operations canonicalDirection, angleApprox and signedAngleApprox are absent

- **Kind:** completeness
- **Location:** `03-Geometry/01-point.hpp:107`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** The 01-point.hpp inventory row (03-Geometry/00-index.md:9) lists `canonicalDirection (gcd-normalized, sign-fixed key); angleApprox; signedAngleApprox`. The header ends at line 107 with polarLess, and no other geometry header defines these three operations. The row is honestly marked `partial ... missing: canonicalDirection, angleApprox, signedAngleApprox`, but under CLAUDE.md ('Never mark a package verified with missing operations') P007 cannot be re-marked verified for this header. The fix is to implement the three operations. canonicalDirection should divide by gcd(|x|,|y|) and fix the sign so that d and -d map to one key, with (0,0) mapping to itself. angleApprox should be atan2(|cross|, dot) on lll-widened values. signedAngleApprox should be atan2(cross, dot). Each needs a comment line and its own oracle in the tester.

## 6. Unary minus and perp narrow implicitly in list-initialization for int8_t/int16_t coordinates

- **Kind:** portability
- **Location:** `03-Geometry/01-point.hpp:25`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** The static_assert accepts any signed integral T, including int8_t and int16_t. For those types `-x` promotes to int. So `return {-x, -y};` (line 25), `return {-x, -y, -z};` (line 49) and perp's `return {-a.y, a.x};` (line 70) need a narrowing conversion inside list-initialization, which is ill-formed under [dcl.init.list]. GCC accepts it with a default-on -Wnarrowing warning, and any -Werror build rejects it. The tester only instantiates int, lng and lll, so this is never exercised. Two possible fixes: write `{T(-x), T(-y)}` (the value is in range under the existing 'vector arithmetic must fit T' contract, so this hides no lossy narrowing), or narrow the static_assert to sizeof(T) >= 4 and record that domain.
- **Repro:** /tmp/p007rev.zON9/n.cpp: Point2<int16_t> a{3,-4}; auto b=-a; auto c=perp(a); Point3<int8_t> d{1,2,3}; auto e=-d;  g++ -std=gnu++20 -O2 n.cpp -> 6 'narrowing conversion ... from int to short int / signed char [-Wnarrowing]' warnings at 01-point.hpp:25,49,70; with -Werror -> 7 error lines, build fails.

## 8. RationalPoint2::approx triggers -Wconversion through an implicit lll to long double conversion

- **Kind:** style
- **Location:** `03-Geometry/02-line_segment.hpp:17`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** In `static_cast<long double>(x) / d`, the denominator `d` (__int128) converts to long double implicitly. With -Wconversion (required by 05-testing.md), GCC 16.2 warns at 17:67 and 17:100: "conversion from '__int128' to 'long double' may change value". 05-testing.md says: "a warning is acceptable only when the bound is stated in the code." The rounding is intended, but nothing in the code states it and the cast is not explicit. Fix: write `static_cast<long double>(x) / static_cast<long double>(d)` and do the same for y. Optionally note in the struct comment that approx rounds each component independently.
