## 1. sparseStep is an inventory operation with no precondition check and no direct test, and it silently returns a wrong state before build

- **Kind:** correctness
- **Location:** `07-Strings/06-aho.hpp:50`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** The inventory row names `sparseStep` as a public operation. Unlike step/matchCount it never calls checkState, so neither `built` nor the range of u is asserted. Before build, failure links are still the default 0, so the call quietly returns a wrong transition instead of failing the assertion. An out-of-range u is UB with assertions on. 01-principles: "A violated precondition (assert) and a valid input with no answer (sentinel/status) are different cases." 06-aho_tester.cpp never calls sparseStep directly (rg count 0); it is covered only indirectly through step in sparse mode. Fix: either drop sparseStep from the inventory row as an internal helper (the header comment at line 14 already calls helpers internal), or add `checkState(u)` at the public entry, keeping an unchecked internal loop for build and step. Then add a direct arbitrary-state test against the longest-suffix oracle.
- **Repro:** AhoCorasick ac; ac.add("ab"); ac.add("bc"); ac.sparseStep(2,'c') returns 0 with no assertion even at -O0 -D_GLIBCXX_DEBUG with assertions on. After ac.build() the same call returns 4 (state "bc"). Reproduced via /tmp/ahorev/s.cpp: output "unbuilt sparseStep(2,'c')=0 / built=4".

## 2. A brace-list text or pattern that begins with a literal 0 does not compile (vector<T> and string_view overloads are ambiguous)

- **Kind:** correctness
- **Location:** `07-Strings/07-suffixarray.hpp:106`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** For T=int, the class has two constructors (line 20: vector<T>; line 21: string_view) and two patternRange overloads (line 85: const vector<T>&; line 106: string_view). A brace list whose first element is the literal 0 converts to string_view as well as to vector<int>: {0} goes through string_view(const char*) with a null-pointer constant, and {0, k} goes through string_view(const char*, size_t). Overload resolution therefore fails. This is a compile error, not a wrong answer, so severity is low. It still breaks a natural call on an integer text, since symbol 0 is ordinary in the sentinel-free domain. Brace lists that start with a nonzero value pick the vector overload and work. Fix: add an initializer_list<T> overload for the constructor and for patternRange, or document that callers must write vector<int>{...}. The tester never uses brace-initialised patterns, so it does not catch this.
- **Repro:** /tmp/p017rev/amb.cpp: `SuffixArray<int> x({0, 1}); x.patternRange({0});` compiled with g++ -std=gnu++20 gives `error: call of overloaded 'SuffixArray(<brace-enclosed initializer list>)' is ambiguous` and `error: call of overloaded 'patternRange(<brace-enclosed initializer list>)' is ambiguous`.

- **Kind:** style
- **Location:** `07-Strings/06-aho.hpp:35`
- **Skeptics unable to refute:** 3 of 3

## 5. Precondition assertions run once per text byte in every scan

- **Kind:** style
- **Location:** `07-Strings/06-aho.hpp:78`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** 03-cpp.md: "An assertion must not change an operation's asymptotic cost and must stay out of hot inner loops; check preconditions once at the entry of an operation." Codeforces runs with assertions enabled. The scan loops in countMatches (140), countPositions (135), stateCounts (123) and forEachMatch (117) call step() each byte, and step re-asserts `built && 0<=u<size()` through checkState. countMatches/countPositions also call matchCount, which asserts again. forEachMatch calls forEachOutput, which asserts again per boundary. avoids (90) goes through safeStep, which costs about three asserts per byte (forbidden, step, forbidden). Each scan already does checkState(0) and the text-size assert at entry, so the per-byte checks are redundant. Measured cost is small: dense countMatches on 5e6 bytes x5 ran 141-144 ms with NDEBUG versus 144-146 ms without, about 2%. It is still a rule violation. Fix: add an unchecked internal transition, e.g. `int next(int u, unsigned char c) const`, plus direct `nodes[u].count` reads for the scan loops. Keep checkState only in the public step/matchCount/forEachOutput entries.
- **Repro:** /tmp/ahorev/b.cpp: 500 random patterns of length 12 over 4 letters, dense, countMatches over a 5,000,000-byte text 5 times. Built with g++ -std=gnu++20 -O2 with and without -DNDEBUG: 144.5/143.4 ms with assertions versus 145.9/141.0 ms without.

## 6. Complexity comments deviate from the required format; symbol z is undefined

- **Kind:** style
- **Location:** `07-Strings/06-aho.hpp:111`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** 03-cpp.md: structures with setup, update and query use `// S: O(...), U: O(...), Q: O(...), M: O(...)`, with `NA` for an inapplicable component, and "Define any other symbol in the same comment." The struct comment (line 4) has S/Q/M but no U, although add() is an update. Either give U for add (O(m * log(sigma + 2)) per pattern of length m) or write NA and keep insertion in S. The method comments at 75-76 (step), 102 (forEachOutput), 111 (forEachMatch), 119 (stateCounts), 127 (countPatterns), 133 (countPositions) and 137 (countMatches) do not use the `// T: O(...), M: O(...)` form. Line 111 uses `z` ("Adds O(z) callback time"), which is defined only in 95-aho.md and not in the header. Fix: rewrite each as `// T: O(...), M: O(...)`, use `out` (the vocabulary symbol for output size) instead of z or define z inline, and add the U component to the struct line.
- **Repro:** sed -n '4,7p;102p;111p;133p' '07-Strings/06-aho.hpp'

## 7. Instantiating with T=bool triggers -Wbool-compare warnings from the byte-path assert

- **Kind:** style
- **Location:** `07-Strings/07-suffixarray.hpp:34`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** `build(bool bytes, ...)` is an ordinary runtime branch, so line 34 `assert(0 <= c && c < 256)` is compiled for every T. With T=bool it warns twice under -Wall: "comparison of constant '0' with boolean expression is always true" and the same for '256'. The tester itself instantiates SuffixArray<bool> (verify(vector<bool>{...})). 05-testing.md requires `-Wall -Wextra -Wconversion` and accepts a warning only when the bound is stated in the code. Fix: wrap the byte branch in `if constexpr (std::is_same_v<T, int>)`, or make the check `assert(std::cmp_less_equal(0, c) && std::cmp_less(c, 256))`, which needs a bool special case, or note the bound in the code.
- **Repro:** /tmp/p017rev/w.cpp builds SuffixArray<bool>(vector<bool>{true,false}). `g++ -std=gnu++20 -O2 -Wall -Wextra -Wconversion` prints `07-suffixarray.hpp:34:41: warning: comparison of constant '0' with boolean expression is always true [-Wbool-compare]` and `34:51: ... '256' ...`.

## 8. Function and lambda bodies close on their own line, breaking the closing-brace rule

- **Kind:** style
- **Location:** `07-Strings/07-suffixarray.hpp:66`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** 03-cpp.md says: "Closing braces: a multi-line block ends on the line of its last statement, `return res;}`. This applies to control blocks, function bodies and lambda bodies." Every multi-line function body in this header ends with a lone `}`: lines 25 (string_view constructor), 66 (build), 77 (lce), 82 (substringLce), 104 (patternRange), 110 (byte patternRange), 122 (longestRepeated), 154 and 162 (both longestCommonSubstring overloads). The bound lambda also ends with `};` alone on line 102. Control blocks inside the bodies do follow the rule. The dependency 02-Data Structures/04-sparsetable.hpp follows it too (`v.push_back(std::move(level)); }}`, `return f(...);}`). Fix: join each closing brace to its last statement, for example `if (with_rmq) { buildRmq(); }}`, `return rmq.query(a, b);}` and `return l;};`.
- **Repro:** rg -n '^    }$|^}$|^        };$' '07-Strings/07-suffixarray.hpp' matches lines 25, 66, 77, 82, 102, 104, 110, 122, 154, 162.

## 9. Complexity comments do not follow the required format: the byte LCS overload has no T/M line and the struct line has no U component

## 10. Closing braces of multi-line function and lambda bodies sit on their own line

- **Kind:** style
- **Location:** `07-Strings/08-palindrome_queries.hpp:12`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** 00-Guidelines/03-cpp.md, Style section: "Closing braces: a multi-line block ends on the line of its last statement, `return res;}`. This applies to control blocks, function bodies and lambda bodies, and nests: `}}`." Decision log 10-decisions.md:204 also says: "Verified headers that used own-line function closes are normalized during re-audit." This re-audit did not normalize them. Four closes in the header break the rule: line 12 (`isPalindrome` body), line 18 (`maybePalindrome` body), line 27 (the `take` lambda ends with `};` on its own line) and line 30 (`longestPalindrome` body). The fix is to attach each close to the last statement, as in `... : m.even[i] >= len / 2;}`, `return h.get(l, r) == h.reverseGet(l, r);}`, `if (...) { ans = p; }};` and `return ans;}`. This is style only. Behavior is unchanged.
- **Repro:** rg -n '^\s*\};?$' '07-Strings/08-palindrome_queries.hpp' lists lines 12, 18, 27 and 30.
