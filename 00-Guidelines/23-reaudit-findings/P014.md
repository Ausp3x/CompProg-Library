## 9. Precondition assert runs inside the sort comparator and per-element loops through Interval::bounds

- **Kind:** style
- **Location:** `06-Miscellaneous/09-interval_algorithms.hpp:37`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** Interval::bounds (line 16) runs assert(l <= r) on every call. finishOrder's sort comparator (line 37) calls bounds twice per comparison, so the assert runs O(n * log(n)) times inside sort's inner loop, and the bounds arithmetic is redone each time. Per-element loops also call bounds again after finishOrder already checked every interval: line 124 (minimumIntervalStabbing), line 137 (maximumIntervalSchedule), and lines 150 and 155 (weightedIntervalSchedule calls bounds twice per item). 03-cpp.md says: "An assertion must not change an operation's asymptotic cost and must stay out of hot inner loops; check preconditions once at the entry of an operation." The asymptotic cost is unchanged, so only the hot-loop part of the rule is broken. Fix: in finishOrder, compute bounds once per interval into a vector<pair<lll,lll>> (asserting there) and sort and return ids keyed on that cached vector. Callers then reuse the cached bounds instead of calling a[i].bounds(domain) again.
- **Repro:** Rule quote above. Inspect line 37: `auto x = a[i].bounds(domain), y = a[j].bounds(domain);` inside the std::sort comparator; each call runs assert(l <= r) at line 16.
