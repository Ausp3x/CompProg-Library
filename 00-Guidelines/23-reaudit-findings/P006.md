## 1. (Low) A moved-from Fenwick keeps its old n while v is empty, so in-contract calls index past the end of v

- **Kind:** correctness
- **Location:** `02-Data Structures/02-fenwick.hpp:13`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** The implicit move constructor moves `v` (which becomes empty) but copies `int n`. The invariant `n == v.size()` breaks. Every entry assertion checks only against `n`, so after `auto b = std::move(a)` a call such as `a.add(0, 1)` or `a.prefixSum(a.n)` passes its precondition and then indexes an empty vector. That is undefined behavior; the build used here caught it only because the template enables libstdc++ assertions. The tester (line 98) only reassigns the moved-from object, so the gap is not exercised. Using a moved-from object is unusual in contest code, which is why this is low severity. DSU and other structures may share the pattern. Fix: either document that a moved-from Fenwick may only be assigned or destroyed, or drop the redundant `n` field and use `int(v.size())`. Dropping it would also remove the risk of public-state drift.
- **Repro:** /tmp/fw_move.cpp: `Fenwick<lng> a(4); auto b = std::move(a); a.add(0, 1);` built with g++ -std=gnu++20 -fsanitize=address,undefined fails with stl_vector.h:1253 "Assertion '__n < this->size()' failed" inside add.

## 2. get() and allQuery() return a dangling reference when T = bool (vector<bool> proxy)

- **Kind:** correctness
- **Location:** `02-Data Structures/03-segmenttree.hpp:28`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** `const T &get(int p) const { ... return tree[base + p]; }` (line 28) and `const T &allQuery() const { return tree[1]; }` (line 29) assume that `vector<T>::operator[] const` returns `const T&`. For T = bool, `vector<bool>::const_reference` is a plain `bool` prvalue, so both functions return a reference to a temporary. That is undefined behavior. The header contract allows any T with an associative f and an identity, and an OR/AND/XOR segment tree over bool is a common case. GCC 16.2 gives `-Wreturn-local-addr` for both lines. At -O2 the program crashes with a segfault. Under -fsanitize=address,undefined it reports 'reference binding to null pointer of type const bool' at 03-segmenttree.hpp:28:78 and 29:46, then a SEGV. The documented promise 'Returned references remain owned by this tree' is false for this T. Fix: declare both return types as `typename vector<T>::const_reference`, which is `const T&` for every T except bool and `bool` for bool. Otherwise add `static_assert(!std::is_same_v<T, bool>)` and document that restriction. Then add a bool payload case to the tester.
- **Repro:** /tmp/segrev/a.cpp: auto orf = [](bool a, bool b) { return a || b; }; SegmentTree<bool, decltype(orf)> t(vector<bool>{false, true, false}, false, orf); const bool &g = t.get(1); const bool &all = t.allQuery(); std::cout << g << ' ' << all; -- g++ -std=gnu++20 -O2 -Wall: warning returning reference to temporary at lines 28 and 29; the run ends in a segmentation fault. With -fsanitize=address,undefined: runtime error 'reference binding to null pointer of type const bool', then AddressSanitizer SEGV.

## 3. A one-element braced initializer picks the size constructor, not the vector constructor

- **Kind:** correctness
- **Location:** `02-Data Structures/05-prefix_sum.hpp:23`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** PrefixSum and DifferenceArray each have `explicit X(int n = 0)` and `explicit X(const vector<T> &a)`. With a one-element braced list, converting `{7}` to `int` is a standard conversion and beats the user-defined conversion to `vector<T>`. So the int constructor wins and the result is n zeros instead of the array [7]. A two-element list such as `{7, 8}` builds the array as expected, so the meaning of a braced argument depends on its length. `std::vector<lng> v({7})` gives [7], so a user following that convention gets a silently wrong prefix table. The same happens at line 68 for DifferenceArray. When T is wider than int and the single element is a non-constant (for example `PrefixSum<lng> p({x})` with `lng x`), the call is instead a narrowing compile error. The tester always writes `vector<lng>{...}` explicitly, so it never exercises this. This is low severity: it is an API trap, not a wrong algorithm. Fix: add a `PrefixSum(std::initializer_list<T> a) : PrefixSum(vector<T>(a)) {}` constructor, and the same for DifferenceArray, so a braced list always means values. Alternatively, document in the struct comment that braced singletons select the size constructor.
- **Repro:** Wrote /tmp/ps/a.cpp: `PrefixSum<lng> p({7}); cout << p.n << ' ' << p.sum(0, 1);` and `DifferenceArray<lng> d({7}); cout << d.n << ' ' << d.values()[0];`. Built with `g++ -std=gnu++20 -O2 -Wall -Wextra -Wconversion` and no warnings: the output is `7 0` for both, where `1 7` is expected. `PrefixSum<lng> q({7, 8}); q.n, q.sum(0, 1)` prints `2 7`.

## 4. A braced singleton like `({5})` builds a size-5 zero array instead of [5]; the generic constructors also allow implicit conversion from int

- **Kind:** correctness
- **Location:** `02-Data Structures/06-sqrt_decomposition.hpp:18`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** Both structs have overloads `(int N, int B=0, ...)` and `(vector<T> a, int B=0, ...)`. For `SqrtDecomp<lng> d({5})`, binding `{5}` to the int parameter is an identity conversion, while building a vector<T> needs a user-defined conversion. The int overload wins, so the result has 5 identity elements instead of one element 5. `SqrtRangeSum<lng> r({5})` does the same. This mismatches the usual container intuition (`vector<lng> v({5})` is [5]) and silently gives wrong sums for a singleton literal. Separately, SqrtDecomp's constructors (lines 18 and 21) are not `explicit`, so `void f(const SqrtDecomp<lng>&); f(7);` compiles and builds a 7-element structure. SqrtRangeSum and the sibling DSU mark their constructors explicit.
- **Repro:** /tmp/sq_b.cpp: `SqrtDecomp<lng> d({5}); SqrtRangeSum<lng> r({5}); cout << d.n << ' ' << d.query(0,d.n) << ' ' << r.n << ' ' << r.sum(0,r.n);` prints `5 0 5 0` (expected n=1, sum 5). `f(7)` with `f(const SqrtDecomp<lng>&)` compiles and prints 7. Fix: mark both SqrtDecomp constructors explicit. Either add an `std::initializer_list<T>` overload or document that the vector form must be spelled `vector<T>{...}`.
