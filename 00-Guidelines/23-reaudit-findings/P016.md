## 1. Mixed-signedness symbol comparison in KmpMatcher::step matches values that differ

- **Kind:** correctness
- **Location:** `07-Strings/01-prefixfunction.hpp:56`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** step(const U &c) compares `c == pattern[state]` across types. The evidence (90-prefix_z.md, "mixed-type non-narrowing") and the tester case "mixed-types-no-narrowing" treat this as comparing values. When one side is unsigned and at least as wide as the other, the usual arithmetic conversions turn a signed -1 into UINT_MAX or ULLONG_MAX, so different values compare equal. kmpOccurrences, prefixOccurrences(pattern,text) and the streaming matcher then report false matches, and -Wall gives -Wsign-compare warnings at lines 56 and 57. The tester only checks the unsigned char vs int pair, where promotion to int happens to keep the values. Fix: compare with `std::cmp_equal` when both types are integral and `==` otherwise, through one helper used at lines 56 and 57. Alternatively, document that mixed-signedness symbol types are outside the domain, and add a uint/int regression test either way.
- **Repro:** /tmp/p016/a.cpp: kmpOccurrences(vector<uint>{UINT_MAX}, vector<int>{-1}) returns {0} (expected {}); kmpOccurrences(vector<ulng>{~0ULL}, vector<int>{-1}) returns {0}; prefixOccurrences(vector<uint>{UINT_MAX}, vector<int>{-1}) returns {2,1} (expected {2,0}). Build with g++ -std=gnu++20 -O2 -Wall -Wextra and you also get -Wsign-compare warnings at lines 56:29 and 57:15.

## 2. prefixOccurrences(pattern, text) needs an iterable text, which contradicts the documented index-only requirement

- **Kind:** correctness
- **Location:** `07-Strings/01-prefixfunction.hpp:85`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** 90-prefix_z.md says: "Constructors require iterable sequences; static prefix/Z functions only require `.size()` and indexing." kmpOccurrences meets this because it indexes text[i]. The sibling overload prefixOccurrences(pattern, text) loops over text with range-for (`for (const auto &c : text)`), so a text type that has only size() and operator[] does not compile. Fix: loop `for (int i = 0; i < n; ++i) { matcher.step(text[i]); ... }` with n = int(text.size()), matching kmpOccurrences. Alternatively, change the contract text.
- **Repro:** /tmp/p016/d.cpp: struct Idx { size_t size() const { return 3; } char operator[](int i) const { return "aba"[i]; } }; kmpOccurrences(string("a"), Idx{}) compiles, but prefixOccurrences(string("a"), Idx{}) fails with "error: 'begin' was not declared in this scope" at line 85.

## 3. Public build/encode/add accept ulng codes with no stated domain; double-prime path silently truncates or leaves residues unreduced

- **Kind:** correctness
- **Location:** `07-Strings/03-stringhash.hpp:43`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** `encode(ulng x)` returns `{uint(x), uint(x)}` without reducing modulo MOD[i]. `add` assumes both inputs are below MOD and does one subtraction in 32-bit `uint`. `build(int n, F code)` is a public inventory operation and passes `encode(code(i))` straight into `add`. Only the vector<uint> constructor checks the symbol range. Neither the header comment nor 91-stringhash.md (which only says 'callers preserve their invariants') states the allowed range of `code` or of `encode`/`add`/`subtract`/`multiply`, against 03-cpp.md: 'Document in the comment above each struct or free function: domain and width limits'. Codes of 2^32 or more are truncated modulo 2^32 instead of reduced modulo p, which gives deterministic collisions between symbols whose residues differ. Codes in [2^32 - MOD, 2^32) make `a[i] += b[i]` wrap in `uint`. Codes in [MOD[0], 2^32) produce unnormalized residues, so equal residues can compare unequal. Fix: state 'code(i) in [0, MOD[0]) for the double-prime variant, any ulng for WRAP64' in the header comment, and either `assert` that range once per build or reduce with `x % MOD[i]` in `encode`.
- **Repro:** /tmp/shr/a.cpp: StringHash<> a, b; a.build(1, [](int){ return (1ULL<<32) + 1; }); b.build(1, [](int){ return 1ULL; }); a.get(0,1) == b.get(0,1) prints 1, although (2^32+1) mod 1000000007 = 294967269 != 1. Also StringHash<>::add(encode(4000000000), encode(4000000000))[0] prints 2705032697, which is above MOD[0]; the correct residue is 999999951.

## 5. Node, newNode and findNode are in the inventory but have no test-map entry, and the header calls them internal

- **Kind:** test-gap
- **Location:** `07-Strings/92-trie_manacher.md:29`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** The P016 inventory row lists `Trie: Node, clear, size, empty, newNode, findNode, ...` as operations, and 01-principles.md requires that "verified means every operation in the inventory row has a test with an independent oracle".
