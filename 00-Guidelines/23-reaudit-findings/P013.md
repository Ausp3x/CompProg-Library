## 1. Three operations named in the inventory row are not implemented: readLine, readDouble, writeDouble

- **Kind:** completeness
- **Location:** `06-Miscellaneous/03-fastio.hpp:14`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** The inventory row (06-Miscellaneous/00-index.md line 11) lists FastInput::readLine, FastInput::readDouble and FastOutput::writeDouble (fixed precision) as operations of this header. None of them is defined in FastInput (lines 13-76) or FastOutput (lines 85-133), so nothing in the tester or the feature-to-test map covers them. The row is correctly marked `partial; missing: readLine, readDouble, writeDouble`, so the status is not overstated. The package cannot move to verified until these operations exist. The evidence document also contradicts the row: 91-fastio.md lines 4-7 say that 'Floating-point conversion, line parsing ... are not implemented here; advanced backends remain with MI05 / 17-fast_io_advanced.hpp', which reads as a deliberate scope exclusion, while the inventory treats them as missing operations of 03-fastio.hpp. Fix: implement readLine (keeping the same status, destination-preservation and Error-precedence contract as readToken), readDouble and writeDouble(x, precision) in this header and add independent oracles (strtod/to_chars for the doubles, a Python line split for readLine) to 03-fastio_tester.cpp and the feature-to-test map. Or, if they belong to MI05, move them to the 17-fast_io_advanced.hpp row and make 91-fastio.md agree. Every other check passed. Correctness: I reasoned through the limit/10 and limit%10 overflow guard, the -(v-1)-1 construction of the signed minimum, the digits10+3 output buffer (40 of 41 bytes used for lll), small-type promotion in U(0)-U(x) and U(10*v+d), EOF versus Error precedence in peek, and sticky output errors. Probe runs agreed: int8 -128, ulll max, char16_t 65535, uint8 255 and lll min round-trip exactly, and unsigned -0 returns Invalid. Every implemented operation has an independent oracle (to_chars, Python bigints, fopencookie fault injection). No `long`, no POSIX calls in the header, std:: qualification follows the closed list, the complexity comment is present and follows the sibling-header convention, braces match the repository convention, and #pragma once plus the direct template include are present. The header is included in 98-Basic.hpp and 99-All.hpp. The tester passes in quick mode (optimized and checked, 32 s) and in full mode with seed 1 (optimized, checked and ASan/UBSan, 81 s). 03-consistency.py reports no errors.
- **Repro:** grep -nE 'readLine|readDouble|writeDouble' '06-Miscellaneous/03-fastio.hpp'  -> no matches; the row in 06-Miscellaneous/00-index.md:11 names all three.

## 2. Inventory operation `ranks (bulk)` is missing from Compression, but the evidence documents say no feature gap remains

- **Kind:** completeness
- **Location:** `06-Miscellaneous/04-compression.hpp:11`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** The inventory row for 04-compression.hpp (06-Miscellaneous/00-index.md:12) names `ranks (bulk)` and marks the row `partial; missing: ranks`. The header has no `ranks` method. It has only the inherited `encode` from 02-Data Structures/07-ordered_set.hpp:48. That is not the same operation: `encode` returns `index(x)`, which gives -1 for values not in the snapshot, while bulk ranks should return the `lowerBound` position in [0,size()] for every query. The row is correctly `partial`, so this is not a false verified claim. The evidence contradicts it, though. 06-Miscellaneous/92-compression_search.md:69 says "no remaining owned feature gap is known" and 06-Miscellaneous/95-p013.md:53 says "No owned implementation feature is left incomplete". The feature-to-test map in 92-compression_search.md:40-53 has no `ranks` row and no test for it. The package cannot go to verified until (a) `vector<int> ranks(const vector<T> &a) const` is added with a `// Q: O(k * log(n + 1)), output O(k)` comment, implemented as `lowerBound` per element (or as a linear merge when the queries are already sorted), and (b) a test is added with an independent oracle: the linear count `lo` already used in checkVector, and Python `bisect_left` in the oracle mode. The two evidence sentences should then be corrected. Fix: add the method and its tests, or remove `ranks (bulk)` from the row with a recorded reason, then update 92-compression_search.md:69 and 95-p013.md:53.
- **Repro:** rg -n 'ranks' '06-Miscellaneous/04-compression.hpp' finds nothing. `Compression<lng> c({1,3}); c.ranks({0,2,4});` does not compile ('struct Compression<long int>' has no member named 'ranks'). The expected result is {0,1,2}, while c.encode({0,2,4}) returns {-1,-1,-1}.

## 4. RealSearchResult (re-exported by the facade) has no complexity comment line

- **Kind:** style
- **Location:** `05-Mathematics/02-search_algorithms.hpp:52`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** Low severity. The only problem found in this review, and it is a style rule. The facade 06-Miscellaneous/05-binarysearch.hpp defines nothing itself, but its inventory row lists RealSearchResult as an exported item. That struct is defined in the canonical Mathematics header, and its comment block (lines 48-51) describes the meaning of its fields but has no `// T: O(...), M: O(...)` line. 03-cpp.md says: "One comment line directly above every struct and free function except template and debug code: `// T: O(...), M: O(...)` for functions and simple structs". Some other result structs in the library already carry such a line (TopologicalResult, ComponentsResult, DagPathResult). Fix: add `// T: O(1), M: O(1)` as the last comment line directly above `struct RealSearchResult {`. This file belongs to package P012, not P013, so make the fix there; the P013 facade needs no change. Checks that passed for P013: the facade has `#pragma once` and one direct relative include, and gave no warnings with -Wall -Wextra -Wpedantic -Wshadow -Wconversion. Two translation units that each include it link cleanly. All 11 operations in the inventory row exist in the canonical header with the documented domains. Each operation is exercised by the reused canonical suite, which has independent oracles: brute-force arrays, a linear-scan minimum, analytic thresholds and minima, and the 15 assertion probes. The 98-Basic.hpp and 99-All.hpp aggregates include the facade. Closing-brace rule, std:: qualification list, complexity lines on the free functions, no `long`, and no POSIX-only calls: all fine. Correctness: std::midpoint rounds toward its first argument, so md+1 and md-1 never overflow in firstTrue, lastTrue or ternSearch, and binSearch never evaluates its endpoints. Manual probes at the extremes were correct: lastTrue(LLONG_MIN, LLONG_MAX, x < LLONG_MAX-1) gives LLONG_MAX-2, and binSearch(LLONG_MAX, LLONG_MIN, x >= 0) gives 0. The golden-section search reuses one evaluation per step; a position-order guard catches drift and a later convergence recheck stops false claims of convergence. Tester quick mode with seed 1 passed: 2 configurations, 214,441 checks, 15 probes, 12 s. Full mode with seed 20260927 passed: optimized, checked and ASan-UBSan, 1,944,079 checks per configuration (matching the evidence), 27 s. 03-consistency.py reported no errors.

## 7. Multi-line blocks close with '; }' instead of the required ';}'

- **Kind:** style
- **Location:** `06-Miscellaneous/07-permutation.hpp:44`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** 03-cpp.md:55 says: 'Closing braces: a multi-line block ends on the line of its last statement, `return res;}`. ... and nests: `}}`'. 10-decisions.md:204 says: 'every multi-line block, including function and lambda bodies, ends `...;}`'. In this header all 35 multi-line closes use a space, for example 'return true; }' (line 19), 'return q; }' (line 26) and 'out = std::move(p); return true; }' (line 136). Line 44 mixes both forms: '... { j = 0; }} }'. The same spacing also appears in other P013 headers, for example 03-fastio.hpp and 09-interval_algorithms.hpp. Low severity, and it may need a ruling on whether the space matters. Fix: if the rule is literal, normalize to ';}' and '}}}'.
- **Repro:** grep -nE ';[ ]+\}+$' '06-Miscellaneous/07-permutation.hpp' | wc -l prints 35. grep -nE ';\}+$' on the same file prints 0.
