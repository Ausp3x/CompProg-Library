## 1. excircle computes the semiperimeter gap x+y-z with avoidable cancellation: large error, or an assert, on well-conditioned thin triangles

- **Kind:** correctness
- **Location:** `03-Geometry/09-triangle.hpp:73`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** `d = min(x, y) - (z - max(x, y))` subtracts nearly equal lengths when the angle at the opposite vertex is close to pi. The exradius and excenter here are well-conditioned in the coordinates: moving a coordinate by one ulp changes the gap only at second order. The loss comes from the formula. For TriangleApprox({0,0},{2,0},{1,h}).excircle(2, c), the reference is r = h/(sqrt(1+h^2)-1), which is 2e6 for h=1e-6 and 2e9 for h=1e-9 (checked with an 80-digit Decimal). The header returns relative errors of 4.0e-9 (h=1e-6), 3.7e-4 (h=1e-8) and 7.8e-2 (h=1e-9, r=1.8447e9 instead of 2e9). At h=1e-10, hypot rounds x and y to exactly 1, d becomes 0 and `assert(d > 0)` aborts, although the exradius 2e10 is representable. The contract does call 'rounded-zero gap' a precondition, but that wording hides an avoidable instability. Evidence lines 60 and 72 put the cancellation only in the tester's reference ('no implementation change'). In fact the implementation has the same cancellation, and the widened tolerance 64*eps*r*perimeter at tester.cpp:209 hides it. The equal-line-distance witness (tester.cpp:203) also cannot detect a wrong d, because the center error moves along the bisector. Fix: when dot(u,v) < 0, use the identity x+y-z = 2*cross(u,v)^2/((x*y - dot(u,v))*(x+y+z)); otherwise keep x+y-z. With this change the relative error is 0 to 2e-19 for h from 1e-3 to 1e-15 (tested in /tmp/trirev/fix.cpp). Then tighten the tester's exradius tolerance and add a thin obtuse excircle regression against a high-precision reference.
- **Repro:** /tmp/trirev/ex.cpp: TriangleApprox t({0,0},{2,0},{1,1e-9L}); CircleApprox c; t.excircle(2,c); -> c.r = 1844674407.37 vs exact 2000000000.0000000004 (rel err 7.8e-2); with h=1e-10L the call aborts on assert(d > 0).

## 2. Full-mode tester fails for seed 1: the Decimal Heron oracle misclassifies exactly degenerate dyadic sides

- **Kind:** test-gap
- **Location:** `96-Local Testing/03-Geometry/09-triangle_tester.py:54`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** This is a tester defect, not a header defect. `heron()` sets `ctx.prec = 160` and then decides `valid = max(a, b, c) <= s` using rounded Decimal sides. The random fixtures (lines 86-92) scale integer sides by 2^k with |k| up to 7000, so each exact value has thousands of decimal digits. In the line-89 branch `c = rng.randint(0, a + b + 2)`, c can equal a+b, which gives an exactly degenerate triangle. Rounding to 160 digits breaks that equality and the oracle writes `valid=0, area=-1`. Seed 1, full mode, produces the sides 1.25, 7.125 and 5.875 times 2^-4096 (strtold gives 0xap-4099, 0xe.4p-4097, 0xb.cp-4097). Since 1.25 + 5.875 = 7.125 exactly, `heronAreaApprox` correctly returns true with area 0, and the tester then reports FAIL 'Heron triangle inequality classification'. The failure message prints the default placeholder strings expected=true actual=false, which are the reverse of the real values (oracle false, library true). The recorded seed 20260927 and quick seeds 1-5 pass, so the evidence run did not reach this case. Each full run has about 300 such random cases and the chance of c == a+b is roughly 1/1000 per case, so many seeds will fail. Fix: classify with exact arithmetic (`fa, fb, fc = map(Fraction, sides); valid = 2 * max(fa, fb, fc) <= fa + fb + fc`), compute the four Heron factors exactly as Fractions, and convert to Decimal only for the square root. Alternatively use a precision large enough for the exact dyadic expansions, as lines 82-85 already do with 11000 digits. Also pass the real booleans to `require` at tester.cpp line 78 so the reproducer is not misleading.
- **Repro:** python3 '96-Local Testing/03-Geometry/09-triangle_tester.py' --mode full --seed 1  -> FAIL 09-triangle ... Heron sides=(1.19687218261902316974334e-1233,6.82217144092843206753705e-1233,5.6252992583094088977937e-1233) operation=Heron triangle inequality classification

## 3. Multi-line closing braces use `; }` instead of the mandated attached `;}`

- **Kind:** style
- **Location:** `03-Geometry/09-triangle.hpp:13`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** 03-cpp.md says: 'Closing braces: a multi-line block ends on the line of its last statement, `return res;}`.' Decision log line 204 says: 'every multi-line block ... ends `...;}`'. Every multi-line function body in this header ends with a space before the brace, for example lines 13, 25, 30, 40, 47, 54-63, 74, 79, 90, 101, 121 and 124 (`area > 0); out = area; return true; }`). The other P007/P008 geometry headers use the same spacing, while 01-Core and 02-Data Structures mostly attach the brace, so this is a folder-wide normalization issue rather than a problem unique to P009. Fix: remove the space before the closing brace of multi-line bodies (`return true;}`) and keep `{ x; }` spacing only for single-line blocks.
- **Repro:** grep -nE ';\s+\}+\s*$' '03-Geometry/09-triangle.hpp' (lines with a multi-line body close, e.g. 13, 40, 47, 124)
