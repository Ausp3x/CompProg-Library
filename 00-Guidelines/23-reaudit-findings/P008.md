## 1. The small-angle switch in angleMinusSin at .01 is too low: up to 2e-15 relative error just above it

- **Kind:** correctness
- **Location:** `03-Geometry/06-circle.hpp:18`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** For x >= .01 the code computes x - std::sin(x) directly. At x = .01 that cancels about 4.8 decimal digits. Measured against __float128 x - sinq(x): relative error is 2.0e-15 at x=.01, 2.5e-16 at .02 and 7.5e-17 at .05. Evaluating the series at the same points gives about 6e-20. So segmentArea, and diskOverlapAreaApprox through it, lose roughly four of long double's 19 digits for sweeps just above the switch. The evidence (91-ge02.md:91) checks only the series' omitted term and does not mention this. It stays inside the tester's 2e-12 tolerance, so this is low severity. Fix: raise the switch to about 0.5 and add two or three more series terms (1 - y/156*(1 - y/210*(1 - y/272))), so the truncation error stays below long-double rounding. Alternatively, document the 1e-15 relative accuracy.
- **Repro:** In /tmp/circrev/c.cpp (built with g++ -std=gnu++20 -O2 ... -lquadmath): circle_detail::angleMinusSin(0.01L) differs from (__float128)x - sinq(x) by a relative 1.998e-15. At x=0.0099999, on the series branch, the relative error is 6.3e-22.

## 2. circleLineIntersectionApprox misclassifies exact integer tangencies along non-axis directions

- **Kind:** correctness
- **Location:** `03-Geometry/06-circle.hpp:67`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** The function normalises the direction first (u = (b - a) / |b - a|, which rounds each component), then takes z = dot(a - c.c, perp(u)) and tests d == c.r exactly. That stacks several roundings, so an exactly tangent line given by integer input often lands on the wrong side of r and returns 0 or 2 points instead of 1. I scanned r in 1..50, a in [-60,60]^2 and directions (3,4), (4,3), (-3,4), (5,12), (12,5), (8,15): 2244 of the 9818 exact tangencies were misclassified. The header disclaims certified topology near degeneracy, but here the error comes from operation order and costs nothing to avoid. Computing z = cross(b - a, a - c.c) / length(b - a) has one rounding (cross is exact for integer-valued long doubles, and hypot is exact for Pythagorean lengths), and it gets all 9818 cases right. Fix: let w = b - a and L = length(w); set z = cross(w, a - c.c) / L (the sign must match perp), keep the foot p = c.c + perp(w) * (z / L), and build u = w / L only for the half-chord offset.
- **Repro:** Compile against the header: circleLineIntersectionApprox(CircleApprox({0,0},1), dpoint(-7,-4), dpoint(-3,-1)).count returns 0. Expected 1, since the integer discriminant r^2*|d|^2 - cross(d,a)^2 = 25 - 25 = 0 (the tangency point is (-0.6, 0.8)). Another case, a=(-53,-41), b=(-49,-38), r=1, returns count=2. Probe program: /tmp/circrev/a.cpp and /tmp/circrev/b.cpp.

## 6. Witnesses for singleton and segment inputs are neither documented nor tested consistently

- **Kind:** test-gap
- **Location:** `03-Geometry/07-rotatingcalipers.hpp:90`
- **Skeptics unable to refute:** 3 of 3
- **Detail:** For n=2, minimumWidthApprox returns edge=0, opposite=1, and for n=1 it returns edge=0, opposite=0 (line 90). For both, every box from degenerateBox keeps edges={-1,-1} (lines 13 and 96-101). The contract comment on lines 21-23 only covers empty inputs ("Empty diameter/width have -1 witnesses; empty boxes have exists=false"). So for nonempty degenerate inputs the width witness is a valid index while the box edge witness is -1, and neither is written down. The tester (line 89) checks only `width.edge` when n<3. Fix: state the n=1 and n=2 witness values for width and boxes in the header comment and in 91-ge02.md, and assert them in verify() for n<3.

## 7. The exhaustive circle-line test never produces a tangency on a non-axis direction

The evidence row (91-ge02.md:98, 'Exhaustive small integer discriminant counts') suggests tangency is covered when it is effectively not. The random quadratic oracle (line 141) deliberately skips near-zero discriminants, so it does not catch this either.
