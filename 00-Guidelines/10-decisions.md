## Foundations (2026-09-27)

- **Profiles.** Three profiles resolve the tension between a reusable high-performance numeric foundation and code that stays practical in contests: costly ISA specialization sits in full Core, where reuse justifies it, and dependent algorithms rely on its portable fallback; the mini profile serves print and copy limits without forcing every user onto a restricted interface ([01-principles.md](01-principles.md), Profiles).
- **Scoped Completeness.** No folder promises every theoretical idea: inventories are living research roadmaps, and "complete" is scoped to the stated family and domain.
- **Evidence.** The verification rules make confidence inspectable by a later maintainer: a test names the contract it covers and an independent reason its expected result is trustworthy, and a green test is evidence about that coverage, not a correctness argument.
- **Archive.** `OLD` keeps hard-to-reconstruct edge behavior while the active layout keeps one canonical implementation per algorithm. Archiving is neither deletion nor endorsement, so new code is still checked against current contracts and independent references.
- **Qualified Standard Names.** The template's `using namespace std` is a convenience; qualifying every name outside the closed list in [03-cpp.md](03-cpp.md) keeps files consistent and makes less common standard facilities explicit.
- **Separate Tools.** Online testing, the notebook and the workspace keep canonical source editing, reproducible submission generation and temporary contest use apart: generated outputs are disposable derivatives with explicit owners, user workspace files are not, and clean-on-success expansion never leaves a half-updated submission set.
- **Sources.** Research scope is explicit because inventories keep evolving: a ledger records what was consulted and which claim it supports, and a candidate list guides future work without implying that it was reviewed.
- **Excluded Notebooks.** "Ateneo/ProgVar notebooks" came up in the first research discussion, but the final reference decision excluded the local `ProgVar.pdf` and `frankenstein.pdf` ([09-sources.md](09-sources.md)).
- **No Versioning.** No versioning or semver requirement was agreed.

## 2026-10-24 Session Tuning

- **Effort (2026-10-24).** In the transcripts of the first 51 verified packages, Opus `/package` sessions cost about 51% cache reads, 25% output and 23% cache writes at list prices, so effort mainly moves output and the number of steps while context size moves the rest. Anthropic's guidance for these models: Opus 5.5 at `medium` matches or beats Opus 5 at `high` on agentic coding and thinks more per turn at `xhigh` and `max`, which are kept for measured gains, with `high` the floor for intelligence-sensitive work; Fable 5.1 runs `high` by default and `xhigh` for the most capability-sensitive work, and un-steered at high effort it elaborates beyond the task. Sessions therefore run Opus at `high` and Fable at `xhigh`. `@reviewer` stays at `xhigh` (a subagent's own effort overrides the session's: `@researcher` recorded `high` inside `xhigh` sessions) and runs on Fable for Core full packages, so it is never weaker than the implementer. Switching models inside a session was rejected: caches are per model, and Sonnet 5.5 reads cache at the Opus 5.5 price. Review findings per package decide whether to revert (user decision) ([CLAUDE.md](../CLAUDE.md), Models and Delegation).
- **`/finish` in One Pass (2026-10-24).** P072's `/finish` took 404 model calls and 91M input tokens, more than the `/package` run it closed (61M), over eight rounds of questions, because every round re-audited. A run now makes one full `@reviewer` audit, asks every decision and whether to land in one round, and verifies its fixes with the suites and a review of its own diff; a later finding is fixed or asked once, never re-audited (user decision). `finish-log.tsv` records each landing's review findings with the session's model and effort, the measure for the effort setting ([finish](../.claude/skills/finish/SKILL.md)).
- **`/pause` and Keep-Alive (2026-10-24).** The user interrupts open sessions for trips of one to two hours. On a subscription the prompt cache lives an hour; after it, the next call stores the whole context again (up to 400k tokens) at twice the input price, while a keep-alive ping reads it at a twentieth, so each bridged hour costs about a fortieth of a cold restart (user decision to keep the cache warm). Pings are one-shot jobs at pinned times 50 minutes apart, because recurring jobs may fire up to 10% of their period late. They need an idle session and an awake computer, and beyond the plan's usage limit the cache lasts five minutes, so `/pause` also writes a handoff that a new session or `/clear` loads. The status line shows the cache's state and expiry, the context against the compaction window, plan usage and the session's list-price cost ([pause](../.claude/skills/pause/SKILL.md)).
- **One Batch per Session, Delegation, Compaction Kept at 400k (2026-10-24).** The two costliest sessions ran several batches in one context (P037: three batches, 367M input tokens, a 965k peak; P027: four, 223M), and 51 open packages have several batches, so such a package runs one batch per session under its batch id, which a package id's brief names (chosen by row status, a package id would move on to the next batch as soon as `/package` marked the current rows verified). Writing testers and running benchmarks go to subagents, which start from a small context instead of re-reading the main one on every call; failure analysis stays in the main session. Replayed at 300k, the sessions since the 400k window would have read 15–23% less input at one more compaction each, an upper bound because the replay ignores files re-read after a compaction, so the window stays at 400k until these changes have run about five packages. The brief prints the package's launch command from the `*-session` presets and flags a session that differs, so the skills that print it need no extra hook ([package](../.claude/skills/package/SKILL.md)).
- **Schedule Ranking (2026-10-24).** Ready packages ran in file order, so P030 (persistent segment tree), on which 15 open packages wait, sat behind packages nothing needs. `plan.py rank` orders each phase's planned packages by support pass, then most basic tier, then most transitive open dependents, each after its prerequisites (user decision); a new package from `/omission-sweep apply` is placed the same way. The checklist shows a verified package as its label only, since its evidence and note are in `plan.py show` and the inventories.

## 2026-10-29 Contribution

The repository opens to contributors on Linux; the user decided each point, and P250 (SUP17–SUP19) implements them.

- **Platforms.** Linux x86-64 is the reference. Windows works through Ubuntu 26.04 on WSL2. Native macOS is dropped, since GCC builds no sanitizer runtimes for Apple Silicon and the tooling needs systemd, `bwrap` and `-static`; macOS works through an arm64 Ubuntu VM once the runners pass x86-only flags only on x86-64, verified by an arm64 cross build under qemu-user.
- **Licence.** CC0-1.0 for original work, as ACL and KACTL, so contest copies need no notice. `95-Resources` stays tracked and is excluded, as is third-party-derived code, which keeps its own licence.
- **Claims and Roles.** A draft pull request on a `Pxxx-<batch>-<user>` branch claims a package. `git config compprog.role` separates the maintainer, whose `/finish` lands on local `master`, from contributors, whose `/finish` stops on their branch. Core full packages stay maintainer-only: their thresholds and the judge factor are measured on the maintainer's machine, and they run on Fable. At SUP17 the user chose that any open pull request on a claim branch claims, so a package marked ready for review stays claimed until `/merge-pr` lands or closes it, and set this clone's role to `maintainer`. After the review the user chose that a contributor claims in the checkout the session works in and that their `/finish` commits without rebasing, so a pushed claim branch is never rewritten and the maintainer rebases on landing; the claim lookup reads the canonical repository (`git config compprog.repo`, default `Ausp3x/CompProg-Library`), so a fork's clone cannot report a claimed package as free. At `/finish` the user extended claims to `/prune` and `/restyle` (verified packages included), kept a contributor's pull request a draft until the package's last batch so that merging an early batch cannot release the claim, and counted only `verified` finish-log lines as a done support batch, matching batches with targets.
- **Merging.** `/merge-pr` gates each pull request locally, with library-external changes shown for the user's yes before anything runs, and sandboxed gates. No CI for now: the local gates run on the reference hardware. Superseded 2026-11-16: a CI workflow reruns the path rules, template check and validator on every push (2026-11-16 Other Agents, Commit hook limits).
- **Parallel Sets.** `plan.py ready` left in-progress packages out of the disjoint set, so a package with one of four batches done was never offered; it now offers the next open batch, and a package live in this clone (worktree or uncommitted files) reserves its folders.
